## Task 04 — D-16..D-23 detail

`SignInForm.tsx` was unwrapped from `<Card max-w-md>` and re-wrapped in
`<AuthShell>` so the two-column branded chrome (left logo/quote panel,
right form column) becomes the source of truth. The render order inside
the AuthShell child slot is now:

```
<header> (h1 + subtitle)
optional <Alert> (generic / unverified)
<OidcButtons>                          ← D-17 OIDC FIRST
<div text-in-rule separator>           ← D-19 "Or with email"
<Form>
  email field
  password field (with absolute-positioned eye toggle)  ← D-23
  rememberDevice checkbox              ← D-21 Better Auth rememberMe passthrough
  forgot-password muted text           ← D-UX2 sentinel
  submit
</Form>
<footer cosmetic sign-up link>          ← D-28
```

The eye toggle is rendered as an absolute sibling of `<FormControl>`
rather than inside its `<Input>` slot because `<FormControl>` is a Radix
`Slot.Root` that forwards `id`+`aria-describedby` to a single direct
child; wrapping the Input would re-bind the password FormLabel to the
wrapper div and break every `getByLabelText(/password/i)` assertion in
the suite. The toggle's accessible name is provided via a visually-hidden
`<span>` rather than `aria-label="Show password"` so it does not collide
with the password label's accessible name (an `aria-label` containing
"password" would otherwise make RTL's `getByLabelText` return the button).
Both findings are documented in colocated source comments.

`OidcButtons.tsx` gains `size="lg"` + `w-full` + `variant="ghost"` for
the generic SSO provider so the brand row reads "primary auth options
first, neutral options last" per the oracle (D-18).

`signInSchema` is extended with `rememberDevice: z.boolean().default(false)`;
the value is forwarded to Better Auth `signIn.email` as `rememberMe`.

## Task 05 — D-24..D-28 detail

`SignUpForm.tsx` mirrors the SignInForm refactor: `<Card>` chrome dropped,
`<AuthShell sideTitle=… sideQuote=…>` adopts the signup-specific
side-panel override (`end-user.signup.shell.sideTitle.text` /
`sideQuote.text`). Both the form and the post-submit "Check your email"
success state share the same shell.

The password-strength meter is an inline `passwordStrength(value)` helper
(exported alongside the component for future reuse) that scores four
signals — length≥12, uppercase, digit, symbol — and maps the result to
one of four band slots: `weak` (red), `fair` (orange), `good` (yellow),
`strong` (green). The meter renders as a 4px progress bar (Tailwind
`h-1 bg-muted` rail with a `h-full transition-all` filler) plus a
band-label `<span>`; rendering is conditional on `passwordValue.length > 0`
so the meter does not flash on initial render.

## W-1 disposition — terms checkbox SCOPE-OUT

Pre-flight `ls apps/web/src/app/(public)/` returned
`[layout.tsx, setup, sign-in, sign-up, verify-email]`. Neither `/terms`
nor `/privacy` exists. Per planner W-1 the terms checkbox is therefore
intentionally omitted from this plan. The `SignUpForm.test.tsx` suite
ships a positive negative pin (`queryByRole("checkbox", {name:/agree
to/i})` returns null) so an accidental future reintroduction would trip
the suite. The lift-out path (extend `signUpSchema` with
`acceptedTerms: z.literal(true)`, wire
`end-user.signup.action.acceptTerms.label` in en+ru, remove the negative
pin) is documented in `.planning/deferred-items.md §18.1.1-04-05`.
