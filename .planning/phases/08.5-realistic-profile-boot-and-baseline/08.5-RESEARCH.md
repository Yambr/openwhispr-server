## Summary

The `load-test-realistic` profile **does not actually run a realistic stack today** — `docker-compose.load-test.yml` overrides the `litellm` service with `openwhispr-mock-litellm:dev` under BOTH `load-test-mock` AND `load-test-realistic` profiles (lines 321–344). The Speaches CPU container is already declared (lines 360–377) but nothing connects it to LiteLLM, no LiteLLM `model_list` entry points `whisper-large-v3` at `http://speaches:8000/v1`, and the api still talks to the mock LiteLLM. Result: today `tools/load-test/scripts/run.sh realistic` boots Speaches but never actually hits it. This is the single biggest missing piece.

The smallest credible bring-up is six additions: (1) a third LiteLLM proxy_config — `litellm_config.realistic.yaml` — that re-routes `whisper-large-v3` to Speaches via `api_base: http://speaches:8000/v1` and keeps OpenRouter/OpenAI reason+realtime aliases pointed at the public providers (matching `speaches-audio.md` Section 1 wiring); (2) a `load-test-realistic`-scoped override block in `docker-compose.load-test.yml` that **un-mocks** litellm under the realistic profile (real `ghcr.io/berriai/litellm:main-v1.83.14-stable` image + that new config file mount); (3) Speaches env var fix — `PRELOAD_MODELS` (canonical, per `speaches/src/speaches/config.py`) replaces the existing `WHISPER_MODEL` which has no preload effect; (4) HF_TOKEN documented in `.env.example` (pyannote-3.1 weights are gated); (5) pre-warm script extended to also hit `/v1/audio/diarization` so first-request cold-start of pyannote doesn't pollute the smoke gate; (6) a phase-scoped baseline scenario in the k6 bundle that runs 5min ramp + 5min sustained + 2min ramp-down at 100 VU (NOT 1000 — Whisper-large-v3 on M-class CPU is ~1× realtime, so 100 VU saturates throughput on a Mac well before the server tier becomes the bottleneck).

The k6 flows are **almost** profile-agnostic — three of four require zero changes (`reason`, `agent-stream`, `transcribe`). `realtime-ws` will pass against real OpenAI Realtime (`gpt-realtime`) because OpenAI sends `session.created` as the first frame and the flow only awaits ONE inbound message before closing. Expected Mac numbers are advisory only: transcribe p95 will land in the 4–15 s range for a 5 s audio clip on Apple-Silicon CPU, reason p95 in the 1–3 s range (network-bound to OpenRouter), agent-stream TTFB in the 0.5–2 s range, realtime-ws roundtrip in the 200–800 ms range (all dominated by upstream provider latency, not by api/pgbouncer/postgres which is what the published numbers will actually demonstrate).

**Primary recommendation:** add `litellm_config.realistic.yaml`, override the litellm service in the realistic profile only (DO NOT remove the mock override from `load-test-mock`), fix Speaches env to `PRELOAD_MODELS`, document `HF_TOKEN` and `GROQ_API_KEY`/`OPENROUTER_API_KEY`/`OPENAI_API_KEY` as required `.env` inputs for the realistic run, and ship a `baseline.ts` k6 scenario at 100 VU × 12 min (5+5+2). Preserve every existing test file — the operator H100 re-run only needs to swap `.env` provider keys + bump VU count.

## Pre-warm strategy

Current `pre-warm-speaches.sh` (Phase 08 Plan 06 Task 5):
- Copies `sample-5s-16k.wav` into the speaches container via `docker cp`.
- POSTs to `http://localhost:8000/v1/audio/transcriptions` with `model=Systran/faster-whisper-large-v3`.

What needs to happen on first realistic boot:
1. Speaches `PRELOAD_MODELS` env causes models to download AT BOOT (not on first request) per `speaches/src/speaches/config.py`. This shifts the 3 GB download from request-time to boot-time. The compose `start_period: 180s` is currently too short for first-ever boot (need ~5–10 min on slow connections). Recommend `start_period: 600s` for first boot OR document that first-ever `up -d --wait` may timeout and operator should `docker compose logs speaches` and re-run up.
2. After health-check passes, pre-warm hits `/v1/audio/transcriptions` once. With preload, this is a warm forward pass (~3–10 s on M3 Max CPU) not a 30 s cold-start.
3. For Mac baseline: DO NOT add diarization warm (out of scope for Mac smoke per §3 G7 recommendation).
4. For operator H100 re-run: add diarization warm in `pre-warm-speaches.sh` (commented out today, uncommented in operator notes).

**Recommended additions to pre-warm:**
- Print model preload status: `docker compose exec -T speaches sh -c 'ls /home/ubuntu/.cache/huggingface/hub/'` and grep for the model dirs as a confidence check.
- If transcribe warm fails: do NOT exit 0 — exit 1 only if `--strict-warm` flag is set. Keep current tolerant default so the smoke gate is the authoritative pass/fail.

## Mac feasibility analysis

### Whisper-large-v3 throughput on Apple Silicon CPU

- faster-whisper-large-v3 via CTranslate2 on M3 Max CPU runs at approximately **0.5–1.0× realtime** for transcription (a 5 s clip takes 5–10 s wall-clock). `[CITED: github.com/SYSTRAN/faster-whisper README benchmarks + Phase 08 RESEARCH §Pitfall 2]`
- 8-core efficiency vs performance cores split: ctranslate2 uses CPU threads = `OMP_NUM_THREADS` (defaults to all cores). Speaches `latest-cpu` image typically respects this.
- **Realistic VU ceiling on Mac:** Each transcribe iteration occupies Speaches for ~5–15 s. The k6 flow mix in `main.ts` is 4 endpoints with weighted iteration; if 25% of iterations hit transcribe, at 100 VUs we get ~25 concurrent transcribe attempts saturating a single Speaches instance.
- Empirical recommendation: **100 VU is the upper Mac ceiling.** Beyond that, transcribe queue depth at Speaches inflates p95 to 60+ s and the test devolves into a measurement of Speaches queue length rather than the api/pgbouncer/postgres tier. At 100 VU, expect transcribe p95 in the 8–20 s range — slow, but proves end-to-end wiring. Operator with H100 will reset baseline to 1000 VU and see p95 < 1 s.

### Per-endpoint expected p95 shape (advisory only)

| Endpoint | Mac M3 Max 100 VU | Why | Operator H100 1000 VU expectation |
|---|---|---|---|
| `/api/transcribe` | 8–20 s | Whisper-large-v3 CPU inference | < 1 s |
| `/api/reason` | 1–3 s | OpenRouter network roundtrip (chat completion) | 1–3 s (same — network bound) |
| `/api/agent/stream` (TTFB) | 0.5–2 s | OpenRouter SSE first byte | 0.5–2 s |
| `/api/agent/stream` (total) | 5–15 s | Full SSE stream completion | 5–15 s |
| `WSS /v1/realtime` (first frame) | 200–800 ms | OpenAI Realtime upgrade + greeting | 200–800 ms |

The numbers Mac vs H100 differ ONLY on transcribe. Everything else is network-bound to public APIs. This is the key insight to document: **the realistic profile on Mac validates the audio plane wiring, the other three flows demonstrate that LLM/realtime work end-to-end against real providers.**

## Pitfalls

### P1. WHISPER_MODEL is not a Speaches env var
**What goes wrong:** Speaches ignores `WHISPER_MODEL` + `WHISPER__MODEL`; model is loaded lazily on first request → first transcribe takes 30–120 s.
**Why:** Canonical env is `PRELOAD_MODELS` (verified in `speaches/src/speaches/config.py`).
**Fix:** Replace env vars in docker-compose.load-test.yml (G3).
**Warning sign:** First transcribe response time > 30 s after Speaches health-check passes.

### P2. HF cache volume path is wrong
**What goes wrong:** `latest-cpu` image runs as `ubuntu` user; HF cache lives at `/home/ubuntu/.cache/huggingface/hub`. Current mount `/root/.cache/huggingface` is owned by root and unwritable → models re-download every `up`.
**Fix:** Change volume mount path to `/home/ubuntu/.cache/huggingface` (G6).
**Warning sign:** `docker compose logs speaches` shows weight download every boot.

### P3. pyannote-3.1 / community-1 weights are HF-gated
**What goes wrong:** First boot without `HF_TOKEN` set → pyannote model download 403s → diarization endpoint 503s.
**Fix:** Document `HF_TOKEN` in `.env.example` as required-for-realistic.
**Warning sign:** Speaches logs `OSError: You are trying to access a gated repo`.

### P4. Apple Silicon Docker Desktop memory ceiling
**What goes wrong:** Speaches needs ~4 GB RAM for Whisper-large-v3 + pyannote loaded. Docker Desktop default is 8 GB. Combined with postgres + 4 pgbouncer + valkey + grafana + tempo + mimir + traefik + api + litellm + speaches, total stack hits 12–16 GB.
**Fix:** Document in plan that operator should bump Docker Desktop memory to 16 GB.
**Warning sign:** Speaches OOM-killed mid-run, or `docker compose up --wait` timeout on memory pressure.

### P5. Port conflicts with existing :443/:8443
**What goes wrong:** Traefik already binds :443 and :8443. Speaches on internal port 8000 is fine (not host-published). LiteLLM internal port 4000 is fine. No conflict expected.
**Fix:** None — verified via `docker-compose.load-test.yml` (no new host ports).
**Warning sign:** N/A.

### P6. agent-stream model alias missing in realistic config
**What goes wrong:** k6 sends `model: "openrouter/anthropic/claude-haiku-4.5"`; if `litellm_config.realistic.yaml` doesn't have this alias AND LiteLLM doesn't auto-resolve openrouter/... wildcards, every agent-stream iteration 400s.
**Fix:** Add explicit alias at plan time, OR verify LiteLLM wildcard openrouter resolution works without a model_list entry (it does in v1.83+, but verify).
**Warning sign:** smoke gate fails on `agent-stream` with upstream_error finish reasons.

### P7. WS upgrade idle timeout
**What goes wrong:** OpenAI Realtime sessions can idle; if Traefik /v1/realtime route doesn't honor 3600s idleConnTimeout, sessions drop mid-baseline.
**Fix:** Phase 04 Plan 05 already wired Traefik 3600s idle timeouts on :8443 entrypoint. No change.
**Warning sign:** mid-run ws_close_code=1006 spikes.

### P8. PRELOAD_MODELS bandwidth
**What goes wrong:** First boot downloads ~3 GB of model weights. On slow connections (< 10 Mbps) this takes 30+ min; Speaches health-check `start_period: 180s` fails.
**Fix:** Bump `start_period: 600s` for first boot. After first boot, models cached in volume → boot is fast.
**Operator note:** Document that first-ever `up -d --wait` may need to be re-run if the 600s buffer is insufficient.

### P9. Speaches CPU image vs realtime endpoint
**What goes wrong:** `latest-cpu` image supports realtime API per Speaches docs (https://speaches.ai/usage/realtime-api/), but inference latency on CPU is dramatic. For baseline we route realtime → OpenAI direct anyway (gpt-realtime via litellm mode:realtime), so Speaches realtime is NOT exercised. If a future plan wires it, p95 will be in the multi-second range on Mac.
**Fix:** Keep realtime → OpenAI direct, don't wire Speaches realtime.
**Warning sign:** N/A unless plan deviates.

### P10. mock-litellm overlay merge precedence
**What goes wrong:** docker-compose multi-file overlay: when both files declare `services.litellm`, the LAST file wins per-field. If we add `docker-compose.load-test.realistic.yml` with the real LiteLLM image but the load-test.yml already overrides `command: []`, the merge may keep `command: []` and the real LiteLLM container starts without arguments → boots with no config.
**Fix:** Either (a) re-state `command:` explicitly in the realistic overlay, or (b) in `docker-compose.load-test.yml` scope the mock override to `load-test-mock` profile ONLY (split into two service entries — but compose disallows duplicate keys). Cleanest: the realistic overlay file `docker-compose.load-test.realistic.yml` MUST re-state every overridden field (`command`, `volumes`, `environment`, `image`, `build: null`) to undo the mock's overrides.
**Warning sign:** litellm container boots but logs `Usage: litellm ...` (no args supplied).

### P11. mode:realtime LiteLLM streams require LITELLM_MASTER_KEY at boot
**What goes wrong:** Even hermetic configs require the master key to be non-empty for the realtime hop; the api's `realtime.ts` proxy header-rewrite needs the master key to inject into the upstream upgrade.
**Fix:** `LITELLM_MASTER_KEY` is already auto-generated by bootstrap.sh. Verified in `.env.example`.
**Warning sign:** WS upgrade 401s when api lacks master key env.

### P12. Pre-warm script container resolution
**What goes wrong:** `pre-warm-speaches.sh` uses `docker compose ps -q speaches` which returns empty if the speaches service isn't running (e.g. wrong profile selected). Currently it exits 0 with a warning — but on Mac realistic this is FATAL because the smoke gate then sees a 30+ s cold start on iter 0.
**Fix:** Change pre-warm exit semantics: if profile is `realistic` and pre-warm fails, exit 1 (fail the run). Or add a `--strict` flag default-on for realistic.
**Warning sign:** smoke gate fails with transcribe TTFB > 30 s on iter 1.
