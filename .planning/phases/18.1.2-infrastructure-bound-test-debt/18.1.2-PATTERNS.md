## 5. BYOK guard refactor — `process.exit` → `throw` (D-07)

**New diff:** `packages/byok-guard/src/index.ts:242` change `process.exit(1)` to `throw new BYOKGuardError(record.message)`. Callers at api + worker entrypoints catch + log fatal + exit at the process boundary.

**Closest analog (entrypoint catch+exit pattern):** `apps/api/src/index.ts:683-687` — production entrypoint already does:
```ts
app.listen({ port, host: "0.0.0.0" }).catch((err) => {
  console.error(err);
  process.exit(1);
});
```
Mirror that shape: catch `BYOKGuardError` at the top-level entrypoint try/catch wrapper, log via Pino (not console — but boot-logger context applies, see `createBootLogger` already imported in byok-guard).

**Analog for typed Error class:** packages already export typed errors (search `class.*Error extends Error` in `packages/`). For BYOK specifically: NEW `BYOKGuardError extends Error` named export co-located in `packages/byok-guard/src/index.ts`.

**What to copy:** the entrypoint `.catch(err => { log; process.exit(1) })` boundary discipline from `apps/api/src/index.ts:683-687`. Library throws; entrypoint exits. This is the user-memory rule (`feedback_no_workarounds_enterprise.md`): "process-boundary failure should be at entrypoint, not in a library".

**Risk:** existing callers may rely on `process.exit(1)` aborting before any subsequent line runs — search for usages (`grep assertBYOKConfig packages apps`) BEFORE refactor; each call site must either be in a `try/catch` already OR get one in the SAME commit. Vitest currently traps `process.exit` as "unexpectedly called" — that's the failure being fixed. Test contract per CONTEXT: "constructor throws on missing env" — RED test asserts `expect(() => assertBYOKConfig(env)).toThrow(BYOKGuardError)`. TDD pair (D-39 2-commit RED+GREEN).
