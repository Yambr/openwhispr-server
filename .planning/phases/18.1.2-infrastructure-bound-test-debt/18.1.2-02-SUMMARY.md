## HALT — operator three-branch recipe (per W-3 + plan rollback §2)

Three branches for landing per-glob serialisation under Vitest 4:

### Branch (a) — workspace-wide `fileParallelism: false`

```ts
// apps/api/vitest.config.ts
defineConfig({ test: { fileParallelism: false, /* ... */ } })
```

- Cost: serialises **all** apps/api tests (unit + integration), not just
  `*.integration.test.ts`. apps/api has many fast unit suites (~40 files);
  CI wall-time grows from O(parallel) to O(serial).
- Win: zero structural change; one-line edit per package config; mechanical.
- Verdict: **acceptable for packages/data + apps/worker** (small unit
  suites, mostly testcontainer-bound). **Not acceptable for apps/api**.

### Branch (b) — migrate to Vitest 4 `projects` config

```ts
// apps/api/vitest.config.ts
defineConfig({
  test: {
    projects: [
      { test: { name: "unit", include: ["**/*.test.ts"],
                exclude: ["**/*.integration.test.ts"] } },
      { test: { name: "integration", include: ["**/*.integration.test.ts"],
                fileParallelism: false } },
    ],
  },
})
```

- Cost: structural refactor — `projects` array shape changes how
  `--filter`, `--coverage`, and root-level `mergeConfig` interact with the
  per-package config; reporter output changes (one project per name);
  needs validation of coverage thresholds inheritance.
- Win: clean per-glob targeting; matches Vitest 4 idiom.
- Verdict: **the right long-term shape** but >1-commit cost; should be its
  own plan (probable phase 18.1.3) once Plan 03 has migrated integration
  tests onto `getSharedPostgres()` (which makes the serialisation a
  belt-and-suspenders backup rather than load-bearing).

### Branch (c) — defer singleThread; rely on `withReuse()` alone

- Cost: keeps the race window described in pitfall §12 (concurrent first-
  callers across vitest workers can race `withReuse()` cache warmup, each
  spawning a container that the daemon will reconcile — visible as 2-3
  brief container starts in the wave's first 500ms).
- Win: zero further work in this plan; Plans 03 + 05 can land on top of
  the fixture as-is; `TESTCONTAINERS_REUSE_ENABLE=true` already collapses
  N→1 containers in the steady state.
- Verdict: **lowest-risk path** for completing the 18.1.2 chain. The
  port-exhaustion RED Plan 02 was meant to address comes overwhelmingly
  from **N test files × 1 container each**, not from **1 file × multiple
  starts**. The fixture alone eliminates the dominant cause; singleThread
  was the belt-and-suspenders second-order fix.

## Recommendation

**Branch (c)** — defer singleThread to follow-up. Land Plans 03 + 05 on
top of the current fixture; measure port-exhaustion / Ryuk failure rate
in CI; only revisit if the data justifies the `projects` refactor (branch
b). This honours D-22 (zero churn beyond plan budget) + D-18 (≤7 commits
per plan) + the plan's own rollback guidance.
