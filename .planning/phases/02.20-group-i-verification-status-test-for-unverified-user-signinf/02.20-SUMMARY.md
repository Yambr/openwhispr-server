# Phase 02.20: signInFixture verified:false branch (Group I closure)

Closes the last residual from Phase 02.18's split-surface analysis: the contract test `verification-status > cookie + unverified` needed a real Better Auth-issued session cookie for `pending@conformance.test` so it could hit `GET /api/auth/verification-status` with cookie auth and observe `{ verified: false }`. But Better Auth's `/api/auth/sign-in/email` correctly rejects unverified users with HTTP 403 EMAIL_NOT_VERIFIED (per `requireEmailVerification: true` in `apps/api/src/auth.ts` — the production posture).

Per advisor research **Option C** (locked in 02.20-CONTEXT.md D-01), the contract-test helper now temporarily flips `users.email_verified=true` via the owner DB pool ONLY long enough to perform the sign-in (which mints a real BA cookie), then immediately reverts in a `try/finally` so the revert fires on success, sign-in throw, AND network error. Empirically verified: `getSession` does NOT re-check `emailVerified` — it is enforced ONLY at sign-in/sign-up entry. The cookie remains valid for the read endpoint while the row reflects unverified state again.

**Production-safety preserved (D-03):** the owner-pool branch is access-gated by `process.env.DATABASE_URL_OWNER` which is contract-test-runner-internal only. ALL non-test callers (production clients, third-party integrations, anyone hitting the public `/api/auth/sign-in/email` endpoint) STILL receive 403 EMAIL_NOT_VERIFIED for unverified users. `requireEmailVerification:true` is unchanged.

## Defect → fix narrative

### Cascade tail from 02.18 / 02.19

Phase 02.18 closed the production-side rate-limiter IP-resolution defect; Phase 02.19 closed the Traefik `forwardedHeaders.trustedIPs` companion so the per-fixture XFF survives the reverse-proxy hop end-to-end. After 02.19, the `verification-status > cookie + unverified` test stopped failing with HTTP 429 (rate-limit dimension closed) and started failing consistently with **403 EMAIL_NOT_VERIFIED** — the orthogonal "Group I" defect class that 02.18 SUMMARY already documented as a Phase 02.20+ candidate.

The 02.20-CONTEXT advisor research surveyed three options:

| Option | Mechanism                                                            | Verdict                                                                  |
| ------ | -------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| A      | Direct-DB session forge (insert into `session` table, sign cookie via BA's HMAC) | **Rejected** — BA upgrade brittleness; cookie format is BA-internal API |
| B      | Test-only `/test/mint-session` API endpoint                          | **Rejected** — perpetual gate-audit burden (every CI/prod boundary risks leaking the test endpoint) |
| C      | Helper-only owner-pool flip-and-revert, no API change                | **Locked** — smallest blast radius; production code untouched; relies only on the verified empirical behavior that `getSession` does not re-check `emailVerified` |

### Fix — `packages/contract-tests/src/helpers/sign-in-fixture.ts`

The verified:false branch (~30 lines) executes:

```ts
if (opts?.verified === false) {
  const ownerUrl = process.env.DATABASE_URL_OWNER;
  if (!ownerUrl) throw new Error("...DATABASE_URL_OWNER not set...");

  const pool = new Pool({ connectionString: ownerUrl, max: 2 });
  try {
    // FLIP
    await pool.query(
      `UPDATE users SET email_verified = true WHERE lower(email) = lower($1)`,
      [email],
    );
    try {
      return await postSignIn(email);  // mints real BA cookie
    } finally {
      // REVERT — guaranteed on success, throw, AND network error
      await pool.query(
        `UPDATE users SET email_verified = false WHERE lower(email) = lower($1)`,
        [email],
      );
    }
  } finally {
    await pool.end();  // pool closed exactly once
  }
}
return postSignIn(email);  // verified path UNCHANGED from Phase 02.18
```

The default (verified user) path is byte-identical to the Phase 02.18 helper — same Origin header forwarding (Group A), same per-call X-Forwarded-For counter (D-02). The `postSignIn()` helper was extracted from the previous body so the verified:false branch can wrap it without duplicating the request shape.

| -------------------------- | --------------------------------------------------------------------------------- | ---------------------------------- |

| Public `/api/auth/sign-in/email` callers | NO — never has direct DB access                                          | 403 EMAIL_NOT_VERIFIED (unchanged) |
| Third-party integrations   | NO                                                                                | 403 EMAIL_NOT_VERIFIED (unchanged) |
| `contract-test-runner`     | YES — set via `env_file: .env` on the compose service inside `openwhispr_internal` | flip-and-revert succeeds; cookie issued |
| `seed` (one-shot)          | YES — same env_file pattern                                                       | already used to bulk-verify fixture rows |

**Production code paths touched: ZERO.** No file under `apps/api/`, no file under `packages/data/`, no migration, no Better Auth config, no Traefik config. The change is bounded entirely to the contract-test surface (`packages/contract-tests/src/helpers/sign-in-fixture.ts`) and the test-runner compose entry.

The `requireEmailVerification: true` posture in `apps/api/src/auth.ts` (Phase 02.7) is unchanged. The only way a real-world unverified user can obtain a session cookie remains the canonical flow: complete email verification, then sign in.

### Why not weaken `requireEmailVerification:true`?

The advisor explicitly ruled this out (D-04). The flag is the production contract — invalidating it would mean every contract test that uses an unverified user becomes ambiguous (is it testing the contract or the relaxed dev posture?), and any operator who copies our `auth.ts` defaults into their own deployment would silently inherit the relaxation. Helper-only Option C keeps the contract intact.

### Mock plumbing footnote

Two test-mechanics decisions worth recording for future maintainers:

1. **`vi.mock("pg", ...)` factory must register BEFORE the module under test resolves its `import { Pool } from "pg"`.** We use `await import("../sign-in-fixture.js")` *inside each test body* (after `vi.mock` at top-level), which is the canonical vitest pattern for hoisted mocks of module-eval imports.
2. **`Pool` is invoked with `new`, so the mock factory must satisfy the `[[Construct]]` slot.** A `vi.fn(() => ({...}))` arrow factory is NOT constructable — vitest emits a warning and throws `is not a constructor` at the `new Pool(...)` site. Use `vi.fn(function PoolMock(this, _opts) { (this as any).query = ...; (this as any).end = ...; })` form instead. This was caught and fixed during the test-author iteration loop, not by reverse-patch.
