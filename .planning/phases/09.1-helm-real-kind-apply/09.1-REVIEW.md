# Phase 09.1 — Chart Fixes Review

## BLOCKING (must fix before next install attempt)

### B1 — `externalsecret.yaml` still ships only 8 keys; F22's 7 new keys absent

**File:** `charts/openwhispr/templates/externalsecret.yaml:38-62`

F22 expanded `secrets.yaml` (helm-values mode) to 15 keys but the ESO template was not updated. In `secrets.mode=eso` (corporate-litellm overlay), ESO writes only `LITELLM_MASTER_KEY … BETTER_AUTH_SECRET` into `<fullname>-secrets`. Consequence:

1. `apps/api/scripts/check-default-secrets.ts` ENTRYPOINT validator fails on missing POSTGRES_APP_PASSWORD/MASTER_KEK/… → api/web/worker CrashLoopBackOff identical to the F22 symptom.
2. `api-deployment.yaml:112` and `worker-deployment.yaml:81` reference `$(POSTGRES_APP_PASSWORD)` inside `DATABASE_URL`. With the var unset, Kubernetes substitutes empty → `postgres://openwhispr_app:@…/openwhispr` → SCRAM auth fails immediately.

**Proposed fix:** add 7 `data:` entries to `externalsecret.yaml` mirroring the helm-values keys, and add a `corporate-litellm` ExternalSecret assertion in `tests/secrets_test.yaml` that counts `spec.data | length == 15`.

### B2 — `secretPresenceProbeCmd` validates only the original 8 keys

**File:** `charts/openwhispr/templates/_helpers.tpl:189-191`

The probe shells through `for k in LITELLM_MASTER_KEY … BETTER_AUTH_SECRET; do … done` — 8 keys. The whole point of the probe is "fail fast at pod start if ESO has not synced yet." After F22 + B1 is fixed, it will silently pass even if ESO has only delivered the legacy 8 — masking exactly the failure mode F22 surfaced. Pair with B1: extend the loop to include the 7 new keys (POSTGRES_APP_PASSWORD is the most load-bearing — needed for `$(…)` substitution at envvar expansion time).

### H1 — F2 regression assertion is tautological

**File:** `charts/openwhispr/tests/ingress_test.yaml:68-70`

09.1-FINDINGS.md F2 promises: "New helm-unittest assertion: `spec.entryPoints[0]` matches the 15-char regex — locks the contract permanently." The actual assertion is `equal: wsrealtime`. A future maintainer who reintroduces `websecure-realtime` would see this fail with a string mismatch, not with the k8s name-ceiling diagnostic. The intended regression catch (a `matchRegex` on `^[a-z0-9]([a-z0-9-]{0,13}[a-z0-9])?$`) is missing. Without that regex, any 16-char-or-more name that isn't literally `websecure-realtime` would slip through unittest and break on real apply. Add the regex assertion.

### H3 — Migrate Job per-revision name guarantees a NEW Job on every `helm upgrade --install`, even no-op

**File:** `charts/openwhispr/templates/migrate-job.yaml:48`

`name: {{ $fullname }}-migrate-{{ .Release.Revision }}` is correct for k8s immutability, but `wait-for-migrate` selects the latest by `creationTimestamp` and demands `.status.succeeded == "1"`. A no-op upgrade (chart values unchanged) still bumps Revision and creates a NEW Job, against which api/web/worker rollout will block for up to 600 s before the new Job is even scheduled by k8s. Acceptable, but worth documenting as an operational quirk — and add `helm test` coverage for `helm upgrade --reuse-values` with no diff.
