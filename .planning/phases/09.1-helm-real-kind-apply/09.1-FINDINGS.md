## F1 — kind host port conflict with running compose stack

**Symptom:** `kind create cluster` exited with `Bind for 0.0.0.0:8443 failed: port is already allocated` on the openwhispr-control-plane container.

**Root cause:** The maintainer's machine runs the production-realistic docker-compose load-test stack (Phase 08.5/08.6) which binds host port `8443` for Traefik. kind tried to publish its own NodePort 30443 → 8443, which collided.

**Fix (kind-config.yaml):** moved host ports to 18080/18443/18444. The cluster-internal NodePorts (30080/30443/30444) and the chart's IngressRoute entrypoints are unchanged. Only the host-side mapping shifted.

**RED-test:** none needed — this is example-script config, not chart template. The next bootstrap re-run is the GREEN proof.

**Commit:** (Phase 09.1 wave 1 — see git log).

## F2 — Traefik entrypoint name `websecure-realtime` exceeds k8s 15-char ContainerPort.name ceiling

**Symptom:** `helm install traefik` exited with:
```
Error: Deployment.apps "traefik" is invalid: spec.template.spec.containers[0].ports[4].name: Invalid value: "websecure-realtime": must be no more than 15 characters
```

**Root cause:** The Traefik 3 Helm chart maps `ports.<name>` to a `ContainerPort.name` directly. K8s enforces the IANA service-name spec — max 15 chars `^[a-z0-9]([a-z0-9-]{0,13}[a-z0-9])?$`. `websecure-realtime` is 18 chars.

**Severity:** **Real chart bug, not kind-only.** Any K8s cluster (EKS/GKE/AKS) would refuse the Traefik install the chart's example overlay produces. Phase 09 helm-unittest did not catch this because the assertion compared a string against `websecure-realtime` — it never validated the name against the k8s schema.

**Fix:**
- New value `ingress.realtimeEntrypointName` (default `wsrealtime`, 10 chars).
- `templates/ingressroute-api-realtime.yaml` reads the value.
- `templates/api-deployment.yaml` preflight initContainer reads the value AND checks for it as a JSON `"name":"..."` field (was a loose `grep` that matched the longer string accidentally).
- `templates/NOTES.txt` echoes the value.
- `examples/traefik-values.yaml` renamed entrypoint to `wsrealtime` everywhere (including additionalArguments forwardedHeaders).
- `examples/kind-bootstrap.sh` renamed Helm --set keys to `ports.wsrealtime.*` + `service.nodePorts.wsrealtime=30444`.
- New helm-unittest assertion: `spec.entryPoints[0]` matches the 15-char regex — locks the contract permanently.

**RED→GREEN test:** `tests/ingress_test.yaml` — assertions updated in the same commit as the templates.

**Commit:** (Phase 09.1 wave 1 — see git log).

## F3 — Pre-install migrate Job deadlocks against CNPG Cluster CR

**Symptom:** `helm install --wait --timeout 8m` exited with:
```
Error: INSTALLATION FAILED: failed pre-install: resource Job/ow/openwhispr-migrate not ready. status: Failed, message: Job Failed. failed: 1/1
```

Init-container `wait-for-postgres` logs showed 30 iterations of `openwhispr-pg-rw:5432 - no response` followed by `FATAL: pg_isready timed out after 60s`.

**Root cause:** Helm orders the release lifecycle as `pre-install hooks → main manifest apply → --wait → post-install hooks`. The migrate Job was a `pre-install,pre-upgrade` hook (weight -5). The CNPG `Cluster` CR (`postgres-cluster.yaml`) was a regular resource, applied AFTER pre-install hooks. So during migrate the `openwhispr-pg-rw` Service did not exist, wait-for-postgres polled a nonexistent target, and the whole release rolled back.

**Severity:** **Real chart bug — would fail on any K8s.** Phase 09 helm-unittest did not catch it because helm-unittest renders templates offline; it never simulates the hook ordering against a live API server.

**Fix (multi-file architectural):**

1. `templates/migrate-job.yaml`:
   - Hook narrowed from `pre-install,pre-upgrade` → `pre-upgrade` only. On `helm install` the Job becomes a regular resource that applies alongside the Cluster CR; wait-for-postgres polls until CNPG bootstraps (60s → 600s ceiling, 30 → 300 iterations × 2s sleep).
   - `activeDeadlineSeconds`: 300 → 900 (covers CNPG bootstrap 90-180s + wait-for-postgres up to 600s + actual migration ~30s).

2. `templates/migrate-serviceaccount.yaml`:
   - Hook annotations removed — SA must persist across releases because api/web/worker reference it indirectly via the new wait-for-migrate Role.
   - New `Role` `<fullname>-migrate-reader` granting `get/watch/list` on the migrate Job + pods.
   - New `RoleBinding` wiring the chart-wide app ServiceAccount to that Role.

3. `templates/_helpers.tpl`:
   - New helper `openwhispr.waitForMigrateInitContainer` rendering a `bitnami/kubectl:1.30.4` initContainer that polls `kubectl get job/<fullname>-migrate -o jsonpath='{.status.succeeded}'` until == "1" (300 iterations × 2s = 600s ceiling).

4. `templates/api-deployment.yaml` + `web-deployment.yaml` + `worker-deployment.yaml`:
   - Inserted `{{- include "openwhispr.waitForMigrateInitContainer" . | nindent 8 }}` as initContainer[0] (before secret-presence-probe). This gates application start until the Job is Complete, replacing the implicit ordering that hooks used to provide.

**RED→GREEN tests:**
- `tests/migrate_test.yaml` — hook value flipped + 3-doc render assertion for SA+Role+RoleBinding + initContainer loop cap raised.
- `tests/api_test.yaml` — initContainer indices shifted: wait-for-migrate[0], secret-presence-probe[1], traefik-preflight[2]. `lengthEqual` updated where preflightCheck=false (was 1 → now 2).
- `tests/web_test.yaml` + `tests/worker_test.yaml` — initContainer[0] flipped to wait-for-migrate, [1] is secret-presence-probe.

helm-unittest total: 107/107 (no count change; assertions enriched).

**Commit:** (Phase 09.1 wave 1 — see git log).

## F4 — CNPG admission webhook rejects `shared_preload_libraries` inside `parameters`

**Symptom:** `helm install` exited with:
```
admission webhook "vcluster.cnpg.io" denied the request: Cluster.postgresql.cnpg.io "openwhispr-pg" is invalid: spec.postgresql.parameters.shared_preload_libraries: Invalid value: "pg_partman_bgw": Can't set fixed configuration parameter
```

**Root cause:** CNPG ≥1.22 manages `shared_preload_libraries` as a "fixed" parameter outside the normal `postgresql.parameters` dict because the operator must coordinate it with extension lifecycle. The correct slot is `spec.postgresql.shared_preload_libraries: [list]` (top-level list, not nested under parameters as a string).

**Severity:** Real chart bug — would fail on any modern CNPG install (≥1.22 = since Jan 2024). helm-unittest does not invoke admission webhooks, so the offline render passed silently.

**Fix:**
- `templates/postgres-cluster.yaml` — moved `shared_preload_libraries: "pg_partman_bgw"` out of `parameters` into top-level `spec.postgresql.shared_preload_libraries: [pg_partman_bgw]` (list).
- `tests/postgres_cluster_test.yaml` — flipped assertion path + added `notExists` on the old `parameters.shared_preload_libraries` to prevent regression.

**Commit:** (Phase 09.1 wave 2 — see git log).

## F10 — Helm hooks are exclusive (a `pre-upgrade` hook does NOT render on `helm install`)

**Symptom:** After F3 narrowed the migrate Job hook to `pre-upgrade` only, the next `helm install` produced api/web/worker pods in `Init:CrashLoopBackOff`. `helm get manifest` showed NO migrate Job in the install manifest at all. wait-for-migrate initContainer polled a nonexistent Job until timeout.

**Root cause:** Helm hook annotations are exclusive — a hook annotated only `pre-upgrade` renders ONLY on `helm upgrade`. F3 over-corrected the F1 deadlock.

**Severity:** Architectural — every install path for the chart was broken between F3 and this fix.

**Fix (advisor-validated pattern, see `gsd-advisor-researcher` consultation):** migrate Job becomes a **regular release resource with no Helm hook annotation**:
- `metadata.name`: `<fullname>-migrate-<.Release.Revision>` (avoids k8s immutable Job spec restriction on `helm upgrade` — each release produces a new Job).
- `spec.ttlSecondsAfterFinished: 3600` (TTL controller, k8s ≥1.23) auto-GCs per-revision Jobs.
- `templates/_helpers.tpl` `wait-for-migrate` initContainer rewritten to query by LABEL not name:
  ```sh
  kubectl get jobs -n <ns> \
    -l app.kubernetes.io/component=migrate,app.kubernetes.io/instance=<release> \
    --sort-by=.metadata.creationTimestamp \
    -o jsonpath='{.items[-1:].status.succeeded}'
  ```
- `templates/migrate-serviceaccount.yaml` Role: dropped `resourceNames` lock so `list` with label selector works.

Trade-offs accepted: `helm rollback` does not re-run an older migration (Drizzle migrations are forward-only anyway). Old per-revision Jobs GC via TTL after 1 hour.

References:
- Helm hook exclusivity: https://helm.sh/docs/topics/charts_hooks/#hook-types
- Bitnami precedent (postgresql-ha, kafka, mariadb-galera suffix Jobs with revision/checksum).

**Commit:** (Phase 09.1 wave 3 — see git log).

## F14 — `openwhispr_owner` has no CREATEDB privilege; migrate fails on litellm-DB auto-create

**Symptom:** Migrate Job exits 1 with:
```
migrate: failed error: permission denied to create database
  code: '42501',
  routine: 'createdb'
```

**Root cause:** `migrate.ts` calls `ensureLitellmDatabase()` (Phase 3 Plan 01 HIGH-1) which `CREATE DATABASE litellm OWNER openwhispr_owner`. CNPG's `bootstrap.initdb.owner` creates the role with default privileges — no CREATEDB. Connecting as that role to create another database is denied.

**Fix:** `templates/postgres-cluster.yaml` adds `spec.bootstrap.initdb.postInitSQL` (runs as superuser in the `postgres` DB BEFORE the app DB is created):
- `ALTER ROLE openwhispr_owner CREATEDB;` — grants the privilege for any future operator-side createdb.
- `CREATE DATABASE litellm OWNER openwhispr_owner;` — pre-creates the DB so migrate.ts's IF-EXISTS branch skips create.

`postInitSQL` is the CNPG-canonical place for superuser-only bootstrap SQL; `postInitApplicationSQL` runs as the application owner inside the app DB and cannot do CREATE DATABASE.

**Commit:** (Phase 09.1 wave 5 — see git log).

## F18 — `partman` schema permission denied for `openwhispr_owner`

**Symptom:** Migration 0011 `SELECT partman.create_parent(...)` aborted with `permission denied for schema partman`.

**Root cause:** `CREATE EXTENSION pg_partman SCHEMA partman` (in postInitApplicationSQL) is executed as the CNPG superuser, not the application owner. The extension functions become superuser-owned with no implicit grant to other roles.

**Fix:** `templates/postgres-cluster.yaml` postInitApplicationSQL adds three GRANTs:
- `GRANT USAGE ON SCHEMA partman TO openwhispr_owner;`
- `GRANT EXECUTE ON ALL FUNCTIONS IN SCHEMA partman TO openwhispr_owner;`
- `GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA partman TO openwhispr_owner;`

## F23 — migrations call `ALTER ROLE openwhispr_app` from owner connection

**Symptom:** After F22 wave reset, retry 8 migrate Job exited with:
```
DO $$ ... EXECUTE 'ALTER ROLE openwhispr_app SET app.tenant_id ...';
cause: permission denied to alter role
```

**Root cause:** Migrations execute `ALTER ROLE openwhispr_app SET app.tenant_id` (per-role GUC bootstrap) under the owner connection. `openwhispr_owner` is not superuser; ALTER ROLE requires either CREATEROLE (too wide) or membership in the target role.

**Fix:** `templates/postgres-cluster.yaml` postInitSQL adds:
- Idempotent `CREATE ROLE openwhispr_app WITH LOGIN NOBYPASSRLS` in a DO-block (password set by CNPG `managed.roles` from pg-app Secret on next reconcile).
- `GRANT openwhispr_app TO openwhispr_owner` — owner becomes member, satisfies ALTER ROLE permission check.

Advisor follow-up applied in same wave: `managed.roles[openwhispr_app].inRoles: [openwhispr_owner]` — CNPG's declarative reconciler treats `inRoles` as authoritative; an empty list would silently REVOKE the GRANT on next reconcile loop, re-breaking migrations days later. Strategic Phase 09.2 plan: replace per-role GUC with `SET LOCAL app.tenant_id` per-transaction (eliminates cross-role coupling entirely).

**Commit:** (Phase 09.1 wave 9 — see git log).

## F24 — CNPG postInitSQL DO-block `$$` collapsed to `$` by shell quoting

**Symptom:** CNPG primary fails to bootstrap; `openwhispr-pg-1-initdb` pod logs:
```
ERROR: syntax error at or near "$"  (SQLSTATE 42601)
query: "DO $\nBEGIN\n  IF NOT EXISTS ... END $;"
→ "Error while bootstrapping data directory" → "Setting up primary" forever.
```

The whole F23 fix never reached Postgres because the entire Cluster CR refused to bootstrap.

**Root cause:** CNPG renders postInitSQL items into a `psql -c "..."` shell invocation. Bare `$$` inside the double-quoted shell string is consumed as `$$` = current shell PID expansion → `$` reaches psql → 42601 syntax. Helm's `|` block scalar passes through unchanged; the corruption is shell-side, not YAML-side.

**Fix:** `templates/postgres-cluster.yaml` doubles the dollar-quote tag: `DO $$$$ ... END $$$$`. Shell collapses `$$$$` → `$$` before psql parses it.

**Commit:** (Phase 09.1 wave 9 — see git log).

## F25 — Postgres 17 ALTER ROLE requires both CREATEROLE AND ADMIN OPTION

**Symptom:** Retry 11 migrate Job exited with:
```
permission denied to alter role
detail: Only roles with the CREATEROLE attribute and the ADMIN option on role "openwhispr_app" may alter this role.
```

**Root cause:** Postgres 17 (CVE-2024-10977 hardening era) requires non-superuser roles to hold BOTH:
- The `CREATEROLE` attribute, AND
- The `ADMIN OPTION` on the specific target role.

F23 granted plain membership (`GRANT openwhispr_app TO openwhispr_owner`) which gave neither. `openwhispr_owner` had no CREATEROLE and the GRANT lacked `WITH ADMIN OPTION`.

**Fix:** `templates/postgres-cluster.yaml` postInitSQL adds:
- `ALTER ROLE openwhispr_owner CREATEROLE` — attribute required by PG 17.
- `GRANT openwhispr_app TO openwhispr_owner WITH ADMIN OPTION` — required by PG 17 to ALTER the target role (was bare membership in F23).
