# Phase 02.21: Group C residuals (3 layered defects → 25/26 GREEN)

Closes the last 3 contract-test failures from the 9-phase cascade tail. Each residual was diagnosed in isolation per CONTEXT D-01, fixed targeted, and verified with reverse-patch RED→GREEN. The contract suite reaches **25 passed | 0 failed | 1 skipped** (the 1 skipped is the AUTH-07 split-host topology test which is gated on a deliberately-non-canonical operator deployment shape — pre-existing intentional skip, not a defect).

The fixes also closed a hidden-cascade dependency: Residual A's not-found handler exposed Residual C's missing /api/_test/* routes (previously masked by the dualAuthHook 401-on-unmatched-route defect — every probe to /api/_test/force-rotate before Residual A returned 401, indistinguishable from "auth required" to a casual reader, when the actual cause was "route never registered because NODE_ENV gate fails in compose").

## Defect → fix narrative

### Residual A — conventions 404 envelope (Commit 30ec8db)

**Symptom:** `GET /api/does-not-exist` returned `401 {"error":"unauthorized"}` instead of `404 {"error":"not found"}`. The conventions.test.ts assertion `expect([404, 405]).toContain(res.status)` failed.

**Root cause:** `dualAuthHook` is registered as a global `onRequest` hook in `buildApp` (apps/api/src/index.ts:158). For unmatched routes, `req.routeOptions?.config?.auth` is undefined — so the per-route opt-out check at the top of the hook (`if (req.routeOptions?.config?.auth === false) return`) fails, the auth check runs, getSession returns null, and the hook throws AuthError → setErrorHandler emits 401. Fastify's default not-found handler never gets a chance to run.

Compounding: no setNotFoundHandler was registered, so even if the dual-auth check were bypassed, Fastify's default 404 body (`{message,error,statusCode}`) would leak through and break the global error envelope contract (D-13 / WIRE-17).

**Fix (2 changes, ~10 lines):**

1. `apps/api/src/error-handler.ts`: register `app.setNotFoundHandler(() => { throw new NotFoundError("not found"); })` so the SAME centralized setErrorHandler emits the canonical envelope at 404. Single emission point preserved.
2. `apps/api/src/middleware/dual-auth.ts`: add `if (req.routeOptions?.url === undefined) return;` at the top of the hook so unmatched routes bypass the auth check entirely and flow to the not-found handler.

**Reverse-patch (RED → GREEN, captured live):**

```

GREEN (restore both):       GET /api/does-not-exist → 404 {"error":"not found"}
```

### Residual B — delete-account cookie cascade (Commit 830cc12)

**Symptom:** After successful `DELETE /api/auth/delete-account`, the SAME cookie jar still authenticated against `GET /api/auth/verification-status` returning `200 {"verified":false}` instead of the cascade-required `401 {"error":"unauthorized"}`.

**Root cause — three layered defects:**

1. **Cookie cache cookie was never cleared.** apps/api/src/auth.ts:195 enables `session.cookieCache: { enabled: true, maxAge: 5*60 }`. Better Auth stores the encoded `{session, user}` payload client-side in a SECOND cookie named `<prefix>.session_data`, signed by BA. Subsequent `getSession()` calls return the cached payload WITHOUT a DB lookup during the 5-min cache TTL — so deleting the `sessions` row in the cascade transaction is irrelevant for the next 5 minutes.
2. **`__Secure-` prefix variant was never cleared.** Better Auth auto-prefixes cookie names with `__Secure-` over HTTPS (compose default + production). The route's bare-prefix `clearCookie("openwhispr.session_token")` call didn't match the actual emitted cookie name `__Secure-openwhispr.session_token`, so the session-token cookie remained intact in the jar AS WELL.
3. **Even when targeting the right name, the clear directive lacked `Secure`.** RFC 6265bis MANDATES that any Set-Cookie touching a `__Secure-` prefixed cookie carry the `Secure` attribute. tough-cookie (used by contract tests) and every browser silently reject clears that don't comply. Verified empirically: the post-fix manual probe before adding `secure:true` showed the jar still containing both `__Secure-` cookies after the DELETE response with non-Secure clear directives.

**Fix:** export `COOKIES_TO_CLEAR_ON_DELETE = [session_token, session_data, __Secure-session_token, __Secure-session_data]` and loop with `clearCookie(name, { path: "/", secure: name.startsWith("__Secure-") })`.

  Tests:      1 failed | 23 passed | 2 skipped (26)

Disabling cookieCache for the cookie-only routes is a security follow-up tracked outside this phase; the cascade-contract behavior is now correct because the DELETE response clears the cache cookie atomically with the row deletion.

### Residual C — token-rotation suite (Commit c81c31c)

**Symptom (initial):** `beforeAll` threw `sign-in failed: 403`, marking the entire token-rotation.test.ts file as failed (0 tests run, 1 file fail).

**Root cause — three layered defects, peeled in order:**

1. **Wrong fixture email (the 403 reported in 02.20).** The test signed in with `rotation-test@local`. The seed (packages/data/src/seed/conformance.ts:36) creates `rotation-test@example.com` — the canonical RFC 2606 reserved-TLD address. Better Auth's email validator rejects `@local` outright with HTTP 400 INVALID_EMAIL. The 403 reported in 02.20 was the post-error rate-limit dimension piling up across full-E2E retries; the actual underlying signal was 400 INVALID_EMAIL on the very first attempt.

2. **`/api/_test/*` routes never registered in compose (exposed by Residual A).** `apps/api/src/routes/test-only.ts` gated registration on `NODE_ENV === 'test'`. AND `apps/api/src/routes/index.ts:95` ALSO gated PLUGIN INCLUSION on the same condition. The compose api container runs with `NODE_ENV=production` (deploy-posture parity), so `POST /api/_test/force-rotate` 404'd in every contract-test run that ever shipped. Before Residual A, the dualAuthHook 401-on-unmatched-route defect masked this — every probe came back 401, indistinguishable from "auth required" to a casual reader. Residual A's clean 404-on-unmatched-route exposed the missing-route reality immediately.

3. **Global rate-limit collapsed the 100 concurrent OLD-bearer assertion.** The contract test fires 100 concurrent requests against `/api/_test/health-authed` to assert the AUTH-04 5-minute overlap window admits the OLD bearer (PITFALLS #8 / D-19 — ZERO 401s allowed during overlap, no retry budget). With the global 60/min/IP default applied, all 100 land in the same per-runner-IP bucket and trip 429 long before the overlap check fires. Verified empirically: post-fix-(1)+(2) probe of 100 concurrent OLD-token requests returned `{ '429': 100 }`.

**Fix:**

- packages/contract-tests/src/token-rotation.test.ts — switch to `rotation-test@example.com`, forward Origin header (BA CSRF gate), mint unique X-Forwarded-For (rate-limit isolation), surface failure body slice in the throw message for future debuggability.
- apps/api/src/routes/test-only.ts — accept `OPENWHISPR_TEST_ROUTES === 'true'` as gate (in addition to NODE_ENV=test). Add `config: { rateLimit: false }` to BOTH `_test` routes — gated behind OPENWHISPR_TEST_ROUTES so production exposure is zero (the routes don't even register).
- apps/api/src/routes/index.ts — match the new env gate so the plugin is added to the route list when compose says so.
- docker-compose.yml — declare `OPENWHISPR_TEST_ROUTES: ${OPENWHISPR_TEST_ROUTES:-false}` on the api service so the env passes through with a SAFE default. Operator self-host = unexposed.
- Makefile — contract-test target prefixes EVERY compose invocation (`up -d --wait`, `seed`, `contract-test-runner`) with `OPENWHISPR_TEST_ROUTES=true` so `make contract-test` works out of the box without the operator needing to remember an env knob.
