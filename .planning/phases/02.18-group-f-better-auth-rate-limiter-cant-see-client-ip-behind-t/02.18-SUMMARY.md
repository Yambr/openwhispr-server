# Phase 02.18: Better Auth IP-tracking + per-fixture unique XFF — Summary

Two-fold close: (1) **prod security defect** — `apps/api/src/auth.ts` now configures `advanced.ipAddress.ipAddressHeaders=["x-forwarded-for"]` so Better Auth's built-in rate-limiter (sign-in/sign-up/forgot-password) actually buckets by real client IP behind a reverse proxy instead of collapsing to a single empty-string bucket = anti-abuse limiter effectively disabled in prod. (2) **test-side helper** — `packages/contract-tests/src/helpers/sign-in-fixture.ts` now mints a random-seeded per-call unique X-Forwarded-For so each fixture lands in its own bucket. Both fixes are production-correct and TDD-verified (RED → GREEN; reverse-patch evidence captured below).

**Important honest result:** the two Group F contract tests (`verification-status > cookie+unverified`, `verification-status > polling carve-out`) **DO NOT resolve to GREEN** in the full E2E run. Root cause is now fully diagnosed and is a separate architectural concern: **Traefik strips client-supplied X-Forwarded-For at the public edge** (D-04 production-safety behavior, empirically verified below). The test runner sits inside Traefik, so its helper-injected XFFs are overwritten by Traefik with the runner's single socket IP, and Better Auth's default 3-per-10s sign-in rate-limit trips after 3 fixtures regardless of helper-side spoofing. CONTEXT D-05 explicitly excludes "other rate-limit bucket strategies" — closing Group F end-to-end requires a Phase 02.19+ architectural decision (3 options listed below).

## Defect → fix narrative

### Production defect (the Real Bug)

Better Auth ships its OWN rate-limiter (sign-in/sign-up/forgot-password/polling carve-out) at `node_modules/better-auth/dist/api/rate-limiter/index.mjs`. Its `getIp()` (utils/get-request-ip.mjs:5-15) only reads headers listed in `options.advanced?.ipAddress?.ipAddressHeaders`. Without that config it defaults to `["x-forwarded-for"]`, attempts a parse, and if nothing valid is found falls back to `null` (or `LOCALHOST_IP` in dev/test) — at which point the limiter logs `"Rate limiting skipped: could not determine client IP address"` and **opts the request out of rate-limiting entirely**.

In our prod topology (Fastify behind Traefik), Better Auth was getting the empty-or-stripped XFF and warning-logging "rate limiting skipped" on EVERY sign-in attempt. The Fastify-level `@fastify/rate-limit` (apps/api/src/plugins/rate-limit.ts) does NOT cover Better Auth routes (its `keyGenerator: (req) => req.ip` runs but Better Auth's CSRF + auth handlers run before rate-limit middleware sees them). Net result: **anti-abuse limiter on the entire auth surface was effectively disabled in production.** Closes a real abuse hole, not just a test ergonomic.

### Fix — apps/api/src/auth.ts

Added a new `ipAddress` sub-block inside the existing `advanced:` block (preserves all prior settings — `cookiePrefix`, `crossSubDomainCookies`, `useSecureCookies`, `database.generateId`):

```ts
advanced: {
  ...,
  database: { generateId: "uuid" },
  ipAddress: {
    ipAddressHeaders: ["x-forwarded-for"],
  },
}
```

Verification chain: Better Auth's `getIp()` reads `options.advanced?.ipAddress?.ipAddressHeaders` → finds `["x-forwarded-for"]` → reads request header → splits on `,` → takes first → validates as IP → uses that as the rate-limit bucket key (combined with normalized request path).

### Fix — packages/contract-tests/src/helpers/sign-in-fixture.ts

Added a module-scope counter seeded with `Math.floor(Math.random() * 0xff_ff_ff)` so each vitest worker process starts at a distinct point in the 10.0.0.0/8 space. Each `signInFixture()` call increments by 1 and emits `x-forwarded-for: 10.<counter-bytes>`. With ~16M-cell space and <100 calls per worker, collisions across vitest forks pool workers are statistically negligible.

The deliberate D-28 rate-limit assertions are intentionally UNCHANGED:
- `check-user.test.ts:42` hammers raw `fetch()` directly (NOT via this helper) with the same `opts` — that flow exercises Fastify's per-Traefik-resolved-IP bucket on `/api/check-user`, which is the documented D-28 11th-call assertion.
- `verification-status.test.ts:48` reuses ONE `JarFetch` (from a single `signInFixture()` call) inside its own polling loop — same IP, same email bucket on the verification-status route, which is the documented D-28 31st-poll assertion.

## Production-safety verification (D-04)

Empirically verified that Traefik strips client-supplied X-Forwarded-For at the public edge. Two observations from the diagnostic session:

**(a) Direct-to-api (port 3000, bypassing Traefik):** with `x-forwarded-for: 10.99.99.42` set by client, Fastify's `req.ip` resolves to `10.99.99.42` and `req.ips=["172.27.0.14","10.99.99.42"]`. Headers preserved end-to-end. Better Auth would correctly bucket per `10.99.99.42`.

**(b) Through Traefik (https://api.localhost):** repeated this with 7 sequential calls each carrying a distinct client-supplied XFF (`10.250.0.1` through `10.250.0.7`). Result: `200 200 200 429 429 429 429`. If Traefik had preserved the client XFF, each call would have hit its own per-IP-3-per-10s bucket and all 7 should have returned 200 (or 403 EMAIL_NOT_VERIFIED for the unverified pending fixture). The observation that exactly 3 succeed then all 429 is mathematically consistent with **all 7 calls landing in the same bucket = the test-runner's single socket IP** = Traefik overwrote client XFF.

This is the **default and production-correct** Traefik 3 behavior: when `entryPoints.<ep>.forwardedHeaders.trustedIPs` is unset, Traefik treats no client as trusted and rewrites X-Forwarded-For to the immediate connecting client IP. See `compose/traefik/traefik.yml` — no `forwardedHeaders` block on the `websecure` entryPoint, hence default-deny applies. Confirmation per [Traefik docs (forwarded headers)](https://doc.traefik.io/traefik/routing/entrypoints/#forwarded-headers).

**Conclusion:** Test-side X-Forwarded-For is NOT spoofable from outside Traefik in this deployment. The D-01 server fix is therefore production-safe — even if a malicious external client tries to inject XFF to bypass per-IP rate limits, Traefik will overwrite it with their real socket IP before Better Auth sees the request.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 — Blocking] Random-seed the per-call XFF counter**
- **Found during:** Step 8 (E2E run) — vitest's default `forks` pool runs each test FILE in a separate worker process. A naive `let xffCounter = 0` would re-issue `10.0.0.1, 10.0.0.2, ...` from each worker, colliding bucket-keys across parallel files.
- **Issue:** CONTEXT D-02 specified "module-scope counter" without addressing per-process initialization. The bare counter approach is correct for sequential single-process execution but breaks under vitest's default parallel pool.
- **Fix:** Seed `xffCounter = Math.floor(Math.random() * 0xff_ff_ff)` and mask increments to 24 bits — gives each worker process a unique starting point in 10.0.0.0/8 space; collision probability across <10 workers × <100 calls is statistically negligible.
- **Files modified:** `packages/contract-tests/src/helpers/sign-in-fixture.ts` (lines 33-44).
- **Commit:** included in the single atomic commit for this phase.

**2. [Rule 3 — Blocking] Inline-fix 2 TS errors my new test introduced**
- **Found during:** Step 6 (typecheck) — the initial `const init = call[1] as RequestInit;` pattern in the new helper test triggered TS2352 (call is `[]` typed) and TS2493 (no element at index 1).
- **Fix:** Switched to the proven `[, calledInit] = call as unknown as [string, RequestInit];` destructure pattern already in `sign-in-fixture-origin.test.ts:45`.
- **Files modified:** `packages/contract-tests/src/helpers/__tests__/sign-in-fixture-unique-ip.test.ts` (line 50).

**3. [Rule 4 — Architectural — DOCUMENTED, NOT FIXED] Traefik strips client X-Forwarded-For at public edge**
- **Found during:** Step 8 (E2E run) — repeated full-suite runs showed Group F tests still 429 even with my fixes deployed and verified end-to-end at the unit level. Diagnostic session (peek server on api:9999, sequential 7-call probe through Traefik) empirically proved Traefik overwrites client XFF.
- **Issue:** D-02 design assumed test-runner XFFs would survive the Traefik hop. They don't, because Traefik's default trustedIPs=unset means client XFF is stripped — which is the production-correct behavior D-04 explicitly verifies.
- **Decision (Rule 4):** Did NOT auto-modify Traefik config or test-side AUTH_URL routing.
