## Deviations from Plan

### NEW defect — Phase 02.8 escalation

**[Rule 4 — architectural escalation] Better Auth user-id generator vs Postgres `uuid` column impedance mismatch**

- **Found during:** Task 2 (live make contract-test)
- **Symptom:** `FAILED_TO_CREATE_USER` from `POST /api/auth/sign-up/email`; underlying Postgres error `invalid input syntax for type uuid: "04xaRzi0ScgyXxWRtKwGG74OkqNZb0yO"` (SQLSTATE 22P02)
- **Root cause:** `packages/data/src/schema/users.ts:17` declares `id: uuid("id").primaryKey().defaultRandom()` — Postgres `uuid` type. Better Auth v1.6.9's default ID generator (in `@better-auth/core/dist/utils/id.mjs`) emits a 32-character base32-style opaque string, not a UUID. The Drizzle adapter explicitly supplies `$1 = id` in the INSERT, bypassing the Postgres `default gen_random_uuid()`. pg rejects the bind parameter at parse time before reaching the function default.
- **Why it surfaces NOW:** Plan 02.7-04 (D-03A) tightened `signUp()` to throw on any non-USER_ALREADY_EXISTS 4xx instead of swallowing all 4xx as "idempotent". Pre-Plan 04, every signup silently failed with this exact 422 and the seed exited 0 with `{created:false}` — leaving the DB unseeded as the proximate cause of 13/26 contract failures. The fail-loud upgrade is doing exactly what it was designed to do: surface the masked root cause.
- **Why this is NOT auto-fixed in Plan 06:** Plan 06 is a pure verification plan (`autonomous: false`, `files_modified: []`) with explicit instruction "ZERO production code changes — pure black-box conformance run". Auto-fixing would (a) violate the plan's contract, (b) violate the CLAUDE.md scope-boundary rule (issue NOT directly caused by Plan 06's own changes), and (c) require an architectural choice between three remediation paths — operator decision territory.
- **Remediation options for Phase 02.8 (or hot-fix Plan 02.7-08):**
    - **Option A (smallest blast radius):** Configure Better Auth `advanced.generateId` (or its v1.6.9 equivalent) to return `crypto.randomUUID()`. One-line change in `apps/api/src/lib/auth.ts` (or wherever Better Auth is constructed). Pros: schema unchanged, all migrations stable, no data backfill. Cons: tied to Better Auth's option API.
    - **Option B (most aligned with Better Auth defaults):** Change `users.id` from `uuid` to `text` per Better Auth's documented expectation. Pros: future-proof against Better Auth 2.x; fewer custom hooks. Cons: schema migration; changes index sizes / FK column types; may require coordination with `accounts.userId` / `sessions.userId` / `verifications.identifier` references.
    - **Option C (defensive hook):** Add a `users.create` hook in Better Auth config that rewrites `data.id = crypto.randomUUID()` before the adapter sees it. Pros: explicit, auditable. Cons: extra indirection, easy to miss for future tables (sessions/accounts may need similar treatment).
- **Recommendation:** Option A for the hot-fix (single-line change, immediate unblock); Option B as a follow-up cleanup in v2 if Better Auth's id semantics are revisited.
- **Files involved (all read-only in Plan 06):** `apps/api/src/lib/auth.ts`, `packages/data/src/schema/users.ts`, `packages/data/migrations/0000_initial.sql`
- **Status:** ESCALATED — STOPPED per plan, awaiting operator decision (which option) and routing to Phase 02.8 (or 02.7-08).
