## Implementation Decisions

### D-01 — Better Auth UUID mode via `advanced.database.generateId: "uuid"`

This is BA's first-class UUID path, not a workaround. Verified resolution chain:

1. `apps/api/src/auth.ts` `advanced:` block — add `database: { generateId: "uuid" }` (modern v1.6+ key, NOT the legacy `advanced.generateId` callback)
2. `@better-auth/core/dist/db/adapter/get-id-field.mjs:12-30` — when `database.generateId === "uuid"` AND adapter declares `supportsUUIDs:true`, BA sets `shouldGenerateId=false`
3. `@better-auth/drizzle-adapter/dist/index.mjs:432` — Drizzle pg adapter declares `supportsUUIDs: provider === "pg"` ✅ (we use `provider:"pg"`)
4. Result: BA stops generating IDs; Postgres `users.id uuid PRIMARY KEY DEFAULT gen_random_uuid()` (already in `0000_initial.sql`) does the work via `defaultRandom()`
5. No JS round-trip; no `crypto.randomUUID()`; native pg-side UUIDs

**Why NOT Option B (schema migration uuid → text):**
- Storage cost: text id ≈33 bytes vs uuid 16 bytes = ~2× per-row PK + every FK + every btree index entry. At 1000 concurrent target with sessions/audit_log/usage_ledger as hot tables, materially worse.
- Loss of `uuid_ops` btree
- Cascades to SECURITY DEFINER `session_lookup_by_token` return type, every test fixture, RLS policies (no change but reverification needed)
- Multi-week migration vs 1-line config change
- Defer to v2 schema-alignment milestone IF justified by future plugin needs (see D-02)

**Why NOT Option C (defensive create-user hook):**
- Strictly worse than D-01: more code, identical effect, only covers user table not session/account/verification
- Rejected as workaround per `feedback_no_workarounds_enterprise.md`

### D-02 — CI lint guard against plugin-bypass risk (residual risk mitigation)

The genuine risk: BA plugins `organization/schema.mjs:1,12,20,27,38` and `anonymous/index.mjs:9,19` import `generateId` directly from `@better-auth/core/utils/id`, **bypassing** `ctx.generateId`. They emit 32-char strings even with our `database.generateId: "uuid"` override. We do NOT use those plugins today (only `bearer()` and `genericOAuth()` are wired in `apps/api/src/auth.ts`).

**Mitigation:** New test `tests/self-tests/better-auth-plugin-uuid-safety.test.ts` (per Phase 02.4 G3 pattern):
- Read `apps/api/src/auth.ts` source
- Extract the `plugins:` array contents
- Maintain an allowlist of UUID-safe BA plugins: `["bearer", "genericOAuth", "jwt"]`
- Maintain a denylist of plugins known to bypass `ctx.generateId`: `["organization", "anonymous"]`
- Fail loud if any denylist plugin appears in the source, OR if any plugin not on the allowlist appears (forces explicit allowlist update — fail-closed)
- Adding a new plugin requires evaluating whether Option B schema migration is needed first

This is the "boring discipline" mechanism that prevents future cascade-tails of the same shape.
