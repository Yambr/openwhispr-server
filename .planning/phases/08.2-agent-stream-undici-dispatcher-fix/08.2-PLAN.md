# Phase 08.2 Umbrella: agent-stream undici dispatcher fix

## Goal

`apps/api/src/routes/agent/stream.ts` upstream call to LiteLLM completes end-to-end (no `upstream_error` from `undici.fetch`), matching the working behaviour of sibling routes (`/api/transcribe`, `/api/reason`) that already use the shared `@openwhispr/litellm-client` built on `undici.request`.

## Decision: Option A (locked by 08.2-RESEARCH.md)

Extend `@openwhispr/litellm-client` with a new `chatCompletionsStream(req): Promise<Dispatcher.ResponseData>` method (undici.request + Node Readable, `bodyTimeout: 0`, forwards `signal`, raises `LitellmUpstreamError` on non-2xx), and replace the inline `undiciFetch` call in `apps/api/src/routes/agent/stream.ts` with a call to it. Convert the upstream Node Readable to a Web ReadableStream via `Readable.toWeb(...)` to keep the existing `sseToNdjson` consumer unchanged.

Option B (explicit `dispatcher:` injection on `undici.fetch`) is rejected per the research scorecard (6.5/8 to A vs 1.5/8 to B). No deviation from research.

## Deferred Items (out of scope for 08.2)

1. **`apps/api/src/routes/tokens/_call-provider.ts:44-55` global-dispatcher stomp.** Latent SSRF bypass: a vanilla `new Agent({ connect: { timeout: 3000 } })` is `setGlobalDispatcher`-ed the first time any `/api/tokens/*` endpoint runs, IF the current global's constructor name is `"Agent"` (which the SSRF dispatcher is). Recommended follow-up: replace global-dispatcher stomp with per-call `headersTimeout: 3000` on the token-mint outbound request. Not the live cause of the agent-stream failure (load-test profile does not exercise `/api/tokens/*`), but a real ticking bomb. → file as Phase 08.3 or fold into Phase 6 hardening.
2. **CI gate asserting `undici` major version == 7.** Research §Pitfall 5: future undici 8.x bump has known fetch+custom-dispatcher regressions that MockAgent would silently absorb. → file as a Phase 9 / repo-hardening task.
3. **Centralize `x-litellm-end-user-id` and spend-logs metadata schema decision.** Research §Open Q1: should `authHeaders()` accept a `userId` parameter and emit it as `openwhispr_user_id` in spend-logs metadata? For 08.2 we adopt the client's existing shape unchanged (canonical) — if a follow-up audit shows billing needs the userId in metadata too, extend the client's `authHeaders` and propagate to all three LiteLLM routes.
4. **`headersTimeout` for slow upstream cold-start.** Research §Pitfall 2: default `undici.request` `headersTimeout` is 30s; under realistic profile (real Speaches with cold model) first-token can exceed that. For 08.2 we keep the undici default (mock-litellm responds in <2s, so it's not the live cause). Follow-up: introduce `LITELLM_HEADERS_TIMEOUT_MS` env override (default 30000) on the new `chatCompletionsStream` method when realistic-profile work resumes.
