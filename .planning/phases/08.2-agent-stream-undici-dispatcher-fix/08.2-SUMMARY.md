## Key Architectural Finding (new — beyond research scope)

Live forensic probing pinpointed that **`undici.request` 7.25 + `signal: AbortSignal` + a custom-wrapped `Agent` (the process-wide SSRF dispatcher) fails at the connect/dispatch boundary** before the socket reaches the upstream. This generalises the failure class that the research had attributed to `undici.fetch` only — the same class affects `undici.request` when a signal is passed. The bug isolation matrix from the live stack:

| bodyTimeout | signal | Result |
|---|---|---|
| default | none | GREEN |
| 0 | none | GREEN |
| default | `abort.signal` | **FAIL (upstream_error)** |
| 0 | `abort.signal` | **FAIL (upstream_error)** |

`transcribe` and `reason` never pass a signal, which is why they continued to work throughout. The 08.2-02 commit `ae0dcc3` lands the empirically-validated fix: route omits `signal` at the call site; client interface keeps `signal?: AbortSignal` so the contract is preserved for non-SSRF callers (Test D in `litellm-client/src/index.test.ts`).

Client-disconnect abort still propagates correctly via two paths:

1. `req.raw.once("close", () => abort.abort())` flips `abort.signal.aborted` so in-route consumers observe the abort; the drain loop checks `raw.writableEnded` on every iteration and breaks on client disconnect.
2. `Readable.toWeb(upstream.body)` cancel propagation destroys the source `Readable` when the consumer breaks, closing the undici socket from the body side rather than via signal.

Existing Test 8 (`AbortController wired via req.raw.once('close')`) continues to pass — it asserts the AC state flips, not undici-side signal handling.
