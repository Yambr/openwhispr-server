## Summary

`apps/api/src/routes/agent/stream.ts:171` calls `undiciFetch(upstreamUrl, …)` with NO explicit `dispatcher:` option. In production the request never reaches `mock-litellm` (verified: zero traffic in mock container logs while curl from inside the same Docker network succeeds), so `undici.fetch` either (a) throws at the connect-or-write boundary against the SSRF-wrapped Agent and the route falls into the `endWithFinish(raw, "upstream_error")` branch on line 186, or (b) sees a non-2xx response and falls into the same branch at line 204. The sibling routes `transcribe` and `reason` succeed against the same upstream via `@openwhispr/litellm-client`, which uses `undici.request` (Node `Readable` body) and inherits the SSRF Agent through `setGlobalDispatcher`.

**Recommended option: A — replace `undiciFetch` with the shared litellm-client (extending it with one new method `chatCompletionsStream` that returns the raw `Dispatcher.ResponseData`).** Rationale: (1) it is the SAME code path that already works at load against mock-litellm for the other two LiteLLM endpoints, (2) `undici.request` + Node `Readable.toWeb()` is the canonical SSE pattern documented by undici maintainers ([discussion #1352](https://github.com/nodejs/undici/discussions/1352)), (3) it consolidates the LiteLLM call surface into one client (currently fragmented — agent-stream re-derives `baseUrl`, `masterKey`, `x-litellm-spend-logs-metadata` shape independently), (4) Option B (explicit `dispatcher:` on fetch) merely papers over whichever undici-fetch-specific edge case is biting us in production without resolving why fetch and request behave differently under the same global Agent.

Process-wide via `setGlobalDispatcher`. Sequence (from `apps/api/src/index.ts:50-57`):

`undici.request` (named import) reads from the global dispatcher when no `dispatcher:` option is passed. Both `request()` and `fetch()` should resolve the global through `Symbol.for('undici.globalDispatcher.2')` (and the wrapper to `.1` for legacy fetch). This is confirmed by [undici discussion #2167](https://github.com/nodejs/undici/discussions/2167): *"Calling setGlobalDispatcher() will affect Node.js's fetch, and it's built that way on purpose."* In our codebase the working `litellm-client` tests inject MockAgent via `setGlobalDispatcher(agent)` and intercept every `undici.request` call — and the broken agent-stream tests do the SAME thing successfully against `undici.fetch`. So the disparity is production-environment-specific (see "Why production fails" below).

### Streaming semantics of the working path

`audioTranscriptions` returns `Dispatcher.ResponseData`. The body is a Node `Readable`. `transcribe.ts:100` calls `await upstream.body.json()` — full buffering. No streaming to the desktop client; the request streams INTO LiteLLM (upload) but the response is collected. Same for `reason.ts:111`.

Crucially, **transcribe + reason do NOT exercise a streaming SSE response**. The current working evidence does not prove `undici.request` works for SSE under the SSRF Agent — it only proves it works for plain JSON responses. The streaming claim must be validated in the new tests.

### Why the route lies inside the spec

The route's "tail" is correct: it consumes a `ReadableStream<Uint8Array>` via `sseToNdjson({ body, acc })` (stream.ts:211) and writes one NDJSON line per chunk (stream.ts:214). The SSE parser is a pure function with 30+ tests of its own — out of scope. The defect is strictly the `undiciFetch` call.

### Observed failure mode (live evidence)

From `runs/2026-05-12T18-00-00Z-mock/diagnostics/forensic-probe-output.json`:
- agent-stream returns **status 200**, headers Content-Type `application/x-ndjson`, body **a single `{"type":"finish","finishReason":"upstream_error","usage":{...}}` chunk**.
- mock-litellm container logs show **zero traffic** to `/v1/chat/completions` from the api during the probe.
- Same upstream from inside the api container via `curl http://litellm:4000/v1/chat/completions` succeeds.

Two paths produce that exact body:
1. `undici.fetch` throws — caught at stream.ts:181-188 → `endWithFinish(raw, "upstream_error")` → log line `agent.stream upstream connect failed`.
2. `undici.fetch` resolves with `!upstream.ok` → stream.ts:199-205 → `endWithFinish(raw, "upstream_error")` → log line `agent.stream upstream non-2xx`.

The operator's follow-up logs (RUN-LOG.md "Run 2 / Operator follow-up") name this as the *upstream_error* finish-chunk. Mock-litellm never being hit eliminates path 2 in the absence of an intermediate proxy returning the non-2xx (Traefik does not sit between api → litellm). **Path 1 is the actual mode.**

### Why production fails while tests pass — candidate causes

The stream.test.ts setup uses `setGlobalDispatcher(new MockAgent({connections:10}))` + `.disableNetConnect()`. The MockAgent intercepts both `undici.request` and `undici.fetch` calls correctly. So `undici.fetch` IS shown to honor `setGlobalDispatcher` in our test environment. The production-specific failure must therefore come from one of:

1. **SSRF Agent's wrapped connector interferes with `undici.fetch`'s connection-pool warm-up.** The connector is built via `buildConnector({ lookup: ssrfLookup })` then wrapped to run `ssrfGuard` first (`ssrf-dispatcher.ts:431-438`). `undici.fetch`'s internal path calls connector slightly differently than `undici.request` does (specifically, fetch uses a `BodyMixin` over a Web `ReadableStream` and may issue connect calls with different `connectOptions` shape). **Confidence: MEDIUM** — plausible but unverified.
2. **OTel undici-instrumentation wrapping `undici.fetch` differently from `undici.request`** when the dispatcher is non-default. `apps/api/src/otel-bootstrap.ts:11` notes "auto-instrument Fastify, undici, pg, ioredis, BullMQ". The instrumentation hooks into undici's `request` dispatch event. With a wrapped Agent the hook may double-wrap fetch's body and emit a body-already-consumed error. **Confidence: LOW** — guessing.
3. **`_call-provider.ts:51` global-dispatcher stomp.** This file overwrites the global dispatcher to a plain `new Agent({connect:{timeout:3000}})` the first time any `/api/tokens/*` endpoint is hit, IF the current global's constructor name is `"Agent"`. Our SSRFDispatcher returns `new Agent({ connect: ssrfConnector })` (`ssrf-dispatcher.ts:439`) whose `constructor.name === "Agent"`. **In the load test profile, /api/tokens/* is NOT exercised, so this is NOT the live cause** — but it is a latent ticking bomb that the planner should note as a separate cleanup. **Confidence: HIGH that it's not THIS failure; HIGH that it's a latent threat.**
4. **A 7.24+ undici regression where a custom `Agent` with a `connect` connector intermittently times out fetch streaming bodies.** [openclaw/openclaw#19147](https://github.com/openclaw/openclaw/issues/19147) and [openclaw/openclaw#46685](https://github.com/openclaw/openclaw/issues/46685) describe symptomatically-similar bugs (createPinnedLookup, fetch failed) with undici 7.x Agents passing custom connect handlers. **Confidence: MEDIUM** — our undici is 7.25 (`apps/api/package.json:undici@7.25.0`) which is precisely in the version range these reports affect.
5. **Web ReadableStream + custom connector deadlock.** undici discussion #1352 explicitly recommends `undici.request` for SSE (`body.setEncoding('utf8'); body.on('data', …)`) and notes "stream piping would be preferable but had implementation challenges" — there is documented friction between fetch's ReadableStream surface and custom dispatcher pipelines. **Confidence: MEDIUM.**

The decisive observation: regardless of which of these is the live root cause, **switching to `undici.request` via the shared litellm-client eliminates the entire class of fetch-specific failure modes**. That is precisely Option A.

## SSRF Dispatcher Contract

### Where it's built

`apps/api/src/lib/ssrf-dispatcher.ts:423` — `makeSSRFDispatcher(opts: SSRFOptions): Dispatcher`. Returns `new Agent({ connect: ssrfConnector })` where `ssrfConnector` is a wrapped `buildConnector({ lookup: ssrfLookup })`.

### Where it's stored

Process-wide via `setGlobalDispatcher(dispatcher)` in `apps/api/src/bootstrap.ts:56`. Called once at startup from `apps/api/src/index.ts:57` BEFORE any route registers. NOT request-scoped, NOT module-level inside any route.

### Interface implemented

- **Yes** to undici's `Agent` (it IS an `Agent` instance, line 439).
- **Yes** to `Dispatcher` (return type).
- **Yes** to WHATWG fetch `dispatcher:` option (because fetch accepts any `Dispatcher`).
- The customization is in the `connect` hook only — every other Agent method (`dispatch`, `close`, `destroy`, `keepAliveTimeout`, pool management) is the default undici behaviour.

### Lookup callback shape

`makeSSRFLookup` (ssrf-dispatcher.ts:218) handles BOTH legacy 3-arg `cb(null, address, family)` AND `{all:true}` array form `cb(null, [{address, family}])`. The undici-v7 net.connect path is `{all:true}` — covered.

### Connect guard (IP-literal path)

`makeSSRFConnectGuard` (ssrf-dispatcher.ts:338) runs SYNCHRONOUSLY before `defaultConnector` for IP-literal hostnames. Hostnames pass through to `defaultConnector` → `ssrfLookup`.

## undici fetch vs request: dispatcher propagation

### Verified findings

1. **`setGlobalDispatcher` IS honored by both `request` and `fetch`** in undici 7.x — confirmed by [undici discussion #2167](https://github.com/nodejs/undici/discussions/2167) ("Calling setGlobalDispatcher() will affect Node.js's fetch, and it's built that way on purpose, so we could modify fetch() and other things") and confirmed empirically by our own `stream.test.ts:170` using MockAgent.
2. **Explicit `dispatcher:` on `fetch()` is supported** ([discussion #2167](https://github.com/nodejs/undici/discussions/2167)): `function myFetch(url, opts) { opts.dispatcher = new MyAgent(); return fetch(url, opts) }`.
3. **`undici.request` returns `Dispatcher.ResponseData`** — `body` is a Node `Readable`. **`undici.fetch` returns the WHATWG `Response`** — `body` is a `ReadableStream<Uint8Array>`. To bridge `request`'s body into `sseToNdjson` (which expects `ReadableStream<Uint8Array>`) use `Readable.toWeb(upstream.body)` (Node `node:stream` standard helper).
4. **Per-request `dispatcher:` precedence over global**: undici documents the per-request option takes precedence, confirmed in discussion #2167 reply chain.
5. **SSE canonical pattern in undici is `request()` not `fetch()`** ([undici discussion #1352](https://github.com/nodejs/undici/discussions/1352)).

### Caveats / known bugs

- undici 7.24+ had at least one DNS-lookup-callback-shape regression around custom dispatchers; the upstream issue tracker shows multiple `fetch failed` reports tied to custom Agents in the 7.x line ([openclaw/openclaw#19147](https://github.com/openclaw/openclaw/issues/19147), [#46685](https://github.com/openclaw/openclaw/issues/46685)). We are pinned at `undici@7.25.0` — squarely inside the affected window.
- undici v8 introduces additional fetch+dispatcher incompatibilities ([openclaw/openclaw#61448](https://github.com/openclaw/openclaw/issues/61448)) — NOT our version, but worth flagging so any future undici bump runs the new agent-stream tests as a regression gate.

## Streaming Semantics for SSE

### Working path (litellm-client `request`)

Returns `res.body` as a Node `Readable`. For an SSE stream you would consume it via Node stream events: `body.setEncoding('utf8'); body.on('data', ...)`. To feed it into our existing `sseToNdjson` (which takes `ReadableStream<Uint8Array>`), use the Node-stdlib `Readable.toWeb(res.body)` adapter. No data is buffered.

### Broken path (agent-stream `fetch`)

Returns `upstream.body` as a `ReadableStream<Uint8Array>` — directly compatible with `sseToNdjson` input. The hand-rolled fetch path was chosen specifically because of this direct compatibility (see the comment at stream.ts:52-59: *"the hand-rolled async generator needs raw stream access that LitellmClient.chatCompletions doesn't expose, so we issue the upstream POST via undici directly"*). This historical justification predates the SSRF dispatcher.

### Recommendation for Option A

Add `chatCompletionsStream(req)` to `LitellmClient` returning `Promise<Dispatcher.ResponseData>` (matches the existing `passthrough` shape — body is a Node `Readable`). In `stream.ts`, convert via `Readable.toWeb(upstream.body)` before passing to `sseToNdjson`. The CONVERSION IS ZERO-COPY — Node's `Readable.toWeb` wraps without copying chunks.

The existing `passthrough(path, args)` method ALREADY supports this shape (`packages/litellm-client/src/index.ts:167`), but it has no streaming-specific affordances (e.g. `bodyTimeout: 0` for long-lived streams, see discussion #1352). The new `chatCompletionsStream` should pass `bodyTimeout: 0` and forward `signal` for client-disconnect aborts. A new method (not a passthrough variant) keeps the API explicit and lets `LitellmUpstreamError` mapping stay in the client.

The smaller-diff appeal of Option B is illusory. ## Pitfalls + Edge Cases

For the planner to convert into task verification steps and RED tests.

1. **`bodyTimeout: 0` for long-lived streams.** Without this, undici applies its default 30s body-read timeout and an SSE stream that goes quiet (model warming up) gets ECONNRESET. Set explicitly on the new `chatCompletionsStream` call site in litellm-client.
2. **`headersTimeout` for slow upstream.** Default is 30s. Realistic profile may need higher for cold-model first-token. Plan for env override (`LITELLM_HEADERS_TIMEOUT_MS` default 30000).
3. **`Readable.toWeb()` and abort signal.** When `req.raw.once("close", () => abort.abort())` fires (stream.ts:141-143), the abort must propagate through Web ReadableStream → Node Readable → undici dispatch. `Readable.toWeb()` propagates `cancel()` upstream to the source Readable, which then `.destroy()`s the underlying undici socket. **Verify in test:** simulate client disconnect, assert upstream socket destroy within 100ms (the existing Test 8 in stream.test.ts already covers this for fetch — adapt for the request path).
4. **`signal` option on `undici.request`.** `undici.request` accepts `signal` like fetch. Confirm by reading [undici Dispatcher docs](https://github.com/nodejs/undici/blob/main/docs/docs/api/Dispatcher.md). The shared litellm-client currently does not pass `signal` for non-streaming chatCompletions (no need) — the new streaming method MUST pass `signal`.
5. **Spend-logs-metadata schema divergence.** stream.ts:163-166 includes `openwhispr_user_id`, the client's `authHeaders` (line 116) only includes `openwhispr_request_id`. Verify which shape is canonical per OBS-04 / D-03 — likely the client's shape is correct because the `user:` body field already carries the userId for billing. The planner should pin the canonical shape in CONTEXT (this is a discretion-area decision).
6. **`x-litellm-end-user-id` header.** Working routes send it (litellm-client `authHeaders`), broken route does not. After Option A, agent-stream will start sending it — verify mock-litellm tolerates extra headers (it does; tests in `compose/mock-litellm/src/server.test.ts` already exercise this header on chatCompletions).
7. **`stream_options.include_usage: true` pass-through.** The current route forwards this (stream.ts:153). The new `chatCompletionsStream` method must allow `extras` to carry it.
8. **Reply.hijack timing.** Current route hijacks BEFORE the upstream await (stream.ts:124). On upstream connect failure that fires path 1 (`endWithFinish`), the hijack is already in effect — synthetic 200 + finish-chunk goes over the wire. The fix must preserve this — DO NOT move hijack after the upstream call, or the centralized error handler will compete to emit a different envelope.
9. **`_call-provider.ts:44-55` global-dispatcher stomp** — latent threat. Once any `/api/tokens/*` endpoint is hit in the same process, `setGlobalDispatcher(new Agent({connect:{timeout:3000}}))` replaces the SSRF dispatcher with a vanilla Agent — silently disabling SSRF for ALL subsequent outbound calls in that process. **This is OUT OF SCOPE for 08.2** but the planner should leave a Deferred-Idea bookmark to close it (likely fix: derive timeout via per-call `headersTimeout: 3000` instead of stomping the global dispatcher).
10. **OTel undici instrumentation order.** `index.ts:50` imports `otel-bootstrap.js` BEFORE `installGlobalSSRF()` so OTel sees the SSRF agent. Option A does not change call shape, so OTel spans for agent-stream upstream will be emitted exactly like transcribe + reason spans — net observability improvement.
11. **No retries on upstream connect failure.** Current route emits a single finish chunk and returns. Option A SHOULD preserve no-retry semantics (a stream that already returned 200 to the client cannot be retried — replay would duplicate user-visible deltas). Make the new `chatCompletionsStream` method explicitly opt-out of retries (`maxRedirections: 0`, no retry plugin).
12. **Request-body cloning.** Not an issue for our case — the upstream body is a static JSON.stringify result, not a streaming body. No re-readability concerns.
13. **Content-Type negotiation.** mock-litellm returns `content-type: text/event-stream` on the streaming endpoint. `undici.request` does not parse SSE — fine, `sseToNdjson` does that. Verify the new method does NOT call `.body.json()` accidentally.

## Common Pitfalls

### Pitfall 1: Forgetting `bodyTimeout: 0` on long-lived streams

**What goes wrong:** Default 30s body timeout kills the SSE stream mid-flight when the model thinks for >30s between tokens (rare but real on cold-start).
**Why:** undici applies `bodyTimeout` to ALL request body reads, including streaming responses.
**How to avoid:** Set `bodyTimeout: 0` explicitly on the streaming variant.
**Warning signs:** Mid-stream `UND_ERR_BODY_TIMEOUT` errors in api logs.

### Pitfall 2: Web ReadableStream `cancel()` not reaching upstream socket

**What goes wrong:** Client disconnects; api emits no finish chunk; upstream LiteLLM call keeps running (cost leak).
**Why:** If `Readable.toWeb()` is used but the consumer doesn't call `.cancel()` on stream-end / break, the underlying Node Readable doesn't `.destroy()`.
**How to avoid:** `sseToNdjson` is the consumer — verify it cancels on break / throw. AbortController.signal in `chatCompletionsStream` is the belt-and-suspenders.
**Warning signs:** Mock-litellm log shows the stream completing AFTER the api client disconnected.

### Pitfall 3: stream.ts:124 hijack-before-await

**What goes wrong:** If a refactor moves the hijack AFTER the upstream call, an upstream-throw will trigger Fastify's centralized error handler and emit a 502 JSON envelope instead of the 200 + finish-chunk pattern.
**Why:** Once hijacked, the centralized handler is bypassed.
**How to avoid:** Preserve the current hijack-before-await ordering. The new `chatCompletionsStream` call replaces the inline `undiciFetch` call EXACTLY in place.
**Warning signs:** Test 11 ("Unauthenticated → 401 BEFORE the handler hijacks the reply") starts failing in a way that the response is empty or has different Content-Type than `application/x-ndjson` for non-401 errors.

### Pitfall 4: `_call-provider.ts` global-dispatcher stomp re-entering scope

**What goes wrong:** Although out of scope for this phase, if any token-mint endpoint fires AHEAD of an agent-stream call in the same process, the SSRF dispatcher is replaced by a vanilla Agent. agent-stream then runs without SSRF protection.
**Why:** `_call-provider.ts:51-53` overwrites the global if the current global's constructor name is `"Agent"`.
**How to avoid:** Out of scope for 08.2 — but the planner should mark this as a Deferred Idea for a follow-up phase.
**Warning signs:** Audit log `security.ssrf_blocked` events stop after the first `/api/tokens/*` call.

### Pitfall 5: undici version drift breaking the new method

**What goes wrong:** A future `undici@8.x` bump silently changes `request` signature or dispatcher semantics, and the test suite passes (MockAgent absorbs the change) while production breaks.
**Why:** undici 7→8 has known fetch+dispatcher regressions ([openclaw/openclaw#61448](https://github.com/openclaw/openclaw/issues/61448)).
**How to avoid:** Pin `undici@7.25.x` in `apps/api/package.json` AND `packages/litellm-client/package.json` (already done). Add a CI gate that asserts `node_modules/undici/package.json` major == 7.
**Warning signs:** Renovate bot opens a PR to bump undici.

## Code Examples

### Reference pattern (proposed `chatCompletionsStream`)

```ts
// packages/litellm-client/src/index.ts (NEW METHOD)
// Source: undici discussion #1352 SSE pattern, adapted to our config shape.
import type { Dispatcher } from "undici";

export interface ChatCompletionsStreamRequest extends ChatCompletionRequest {
  signal?: AbortSignal;
  /** Optional override; defaults to 0 (no body timeout — long-lived SSE). */
  bodyTimeout?: number;
}

async chatCompletionsStream(req: ChatCompletionsStreamRequest): Promise<Dispatcher.ResponseData> {
  const model = req.model ?? config.defaultChatModel;
  checkProviderKey(model);
  const body = JSON.stringify({
    ...req.extras,
    model,
    messages: req.messages,
    user: req.userId,
    stream: true,
    stream_options: { include_usage: true, ...((req.extras as { stream_options?: object })?.stream_options ?? {}) },
  });
  const res = await doRequest(`${config.baseUrl}/v1/chat/completions`, {
    method: "POST",
    headers: { ...authHeaders(req.userId, req.requestId), "content-type": "application/json" },
    body,
    bodyTimeout: req.bodyTimeout ?? 0,
    ...(req.signal ? { signal: req.signal } : {}),
  });
  // NOTE: do NOT call ensureOk() here — for SSE the body is consumed by
  // the caller via Readable.toWeb. Caller inspects res.statusCode itself
  // and maps non-2xx to upstream_error via LitellmUpstreamError.
  if (res.statusCode >= 400) {
    const bodyText = await res.body.text();
    throw new LitellmUpstreamError(res.statusCode, bodyText);
  }
  return res;
}
```
