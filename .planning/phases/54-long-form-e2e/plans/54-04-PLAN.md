```json
{
  "test:e2e:acceptance": "PLAYWRIGHT_SKIP_WEBSERVER=1 OPENWHISPR_TOPOLOGY=slim playwright test --project=slim tests/e2e/100-acceptance --reporter=line",
  "test:e2e:acceptance:flake": "for i in 1 2 3; do echo \"--- Acceptance run $i/3 ---\" && pnpm -s test:e2e:acceptance || exit 1; done"
}
```

The flake-guard script uses a POSIX shell `for` loop with explicit `|| exit 1`
to bail on the first failure. This works on macOS + Linux developer machines
+ standard GitHub Actions ubuntu-latest runners. It does NOT use bash-isms
that would break on dash; the `for i in 1 2 3` form is POSIX.

<risks>
- **Bash-isms in package.json scripts:** the `for i in 1 2 3` POSIX form is portable but some shells parse the embedded `&&` + `||` differently. Mitigation: test the script on the developer's local zsh AND in a `sh -c "$(cat the-script)"` invocation. If portability bites, fall back to a `tools/flake-guard.sh` shell file referenced from package.json instead of inlining.
- **Wall-clock budget overrun:** 3 × 60s = 3 minutes. If 54-02 or 54-03 land at 70-80s each (over PRD's 60s ceiling), the flake guard runs ~4-5 minutes and a future CI job could time out on default 5-minute runners. Mitigation: if individual spec runtime exceeds 60s, that's a 54-02/54-03 regression — diagnose there, not here.
- **Better Auth rate-limit between runs:** the password-reset path in 54-03 hits Better Auth's per-email cooldown. Three runs back-to-back may trigger the cooldown on runs 2 + 3. If 54-03's spec is correctly written against the security-envelope confirmation UI (which renders the SAME copy regardless of whether the email actually went out — the standard "if your email is registered..." pattern), this is a non-issue. If 54-03 instead asserts a mailpit fetch with no fallback, the flake guard will catch the bug — which is the WHOLE POINT of the flake guard. Treat any failure as a real bug per PRD.
- **CI hook deferral is policy-permissible:** PRD §non-functional acceptance: "Three consecutive runs of the new spec pass without flake" — does NOT require a CI workflow. The plan lands the script + runbook + deferred-item explicitly so the next phase has a clear pickup. Do not let scope-creep this plan into adding a .github/workflows/ entry.
</risks>
