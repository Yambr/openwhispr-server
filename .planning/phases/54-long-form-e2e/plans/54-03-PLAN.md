<objective>
Implement PRD step 9 (password-reset reachability) as a SEPARATE spec from
the long-form acceptance flow. The reset-password path is independent of the
sign-up flow — splitting it into its own spec keeps each spec under ~60s and
lets the flake guard in 54-04 target either spec selectively.

Purpose: PRD §9 is explicit: "verify the password-reset path is reachable.
Do NOT actually reset the password — just prove the flow is wired." This
proves three real-stack assertions:
1. The "Forgot password?" link on /sign-in is wired.
2. POST /api/auth/forget-password (or whatever route Better Auth exposes)
   triggers a real reset email through the SMTP → mailpit pipeline.
3. The reset link in the email points at /reset-password?token=... and
   the web app renders that route without 4xx/5xx.

Output: One spec file under apps/web/tests/e2e/100-acceptance/.
</objective>

<risks>
- **Reset-request rate limit:** Better Auth has a per-email cooldown on password-reset requests (typically 60s). If this spec runs back-to-back in a flake-guard loop (54-04), the 2nd + 3rd invocations may hit a "please wait" UI instead of the confirmation. Mitigation options: (a) check whether the confirmation UI is a generic "if your email is registered, we sent a reset link" envelope that renders even on rate-limit (security best practice — Better Auth likely does this), (b) randomise the fixture email per run (alice+${Date.now()}@... and pre-provision via API in beforeAll). Pick (a) if Better Auth's response shape allows; otherwise (b).
- **Reset link invalidates prior tokens:** if step 4 of the spec runs and Better Auth invalidates ALL prior reset tokens on a new request, the flake-guard re-runs are fine (each run mints + uses its own token). But if a prior run's token is still pending in Postgres, the new request may collide. Mitigation: rely on Better Auth's standard behaviour (latest token wins, prior tokens orphaned).
- **Alice+0 fixture user's email may differ under slim:** fixtures/auth.ts line 54-56 derives the email from workerIndex. Under slim workers=1, parallelIndex=0 → alice+0@test.local. Confirm this matches what global-setup.ts actually provisioned by reading global-setup.ts before hardcoding the email.
- **/forgot-password vs /reset-password/request route name:** Task 1 discovery is non-negotiable. Do NOT guess the route name — read the actual app routes first. If neither route exists, this phase has uncovered a real PRD-blocking gap → file as BUG-54-* and HALT the plan until the missing route is built.
- **Russian locale leak from 54-02:** if 54-02 and 54-03 run back-to-back and 54-02 fails mid-way leaving the locale cookie in Russian, the "Forgot password?" link selector in 54-03 fails. Mitigation: 54-03 sets the locale cookie explicitly to `en` via `context.addCookies` in beforeEach.
</risks>
