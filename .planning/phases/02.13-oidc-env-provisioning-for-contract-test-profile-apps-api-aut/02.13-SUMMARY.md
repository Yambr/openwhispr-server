# Phase 02.13: OIDC env provisioning for contract-test fixture-idp — Summary

Closes Phase 02.12 cascade tail Group B: the 5 oauth-redirect contract tests no longer return HTTP 503 because `apps/api/src/auth.ts:81-86` now sees populated `OIDC_ISSUER_URL` / `OIDC_CLIENT_ID` / `OIDC_CLIENT_SECRET` env vars on container boot and registers Better Auth's genericOAuth plugin. The defaults point at the contract-test `fixture-idp` service (already running in the contract-test profile, lazy-discovery so default-profile boot is unaffected).

## Defect → fix narrative

**Symptom (Phase 02.12 cascade tail Group B, 5 failing tests):** `oauth-redirect.test.ts` 5 assertions returned HTTP 503 from `/api/desktop-signin/oidc?...` because the genericOAuth Better Auth plugin was never registered.

**Root cause:** `apps/api/src/auth.ts` `readOidcProviders()` returns `[]` when any of the three OIDC_* env vars is unset. The api container's compose environment block did not set them; the contract-test profile already runs `fixture-idp` on `http://fixture-idp:9000` (`docker-compose.yml:347-360`) but no env wired it up.

**Fix:** Add three env lines to `docker-compose.yml` api service environment:

```yaml
OIDC_ISSUER_URL: ${OIDC_ISSUER_URL:-http://fixture-idp:9000}
OIDC_CLIENT_ID: ${OIDC_CLIENT_ID:-conformance-test-client}
OIDC_CLIENT_SECRET: ${OIDC_CLIENT_SECRET:-conformance-test-secret-do-not-use-in-prod}
```

Better Auth's genericOAuth uses **lazy discovery** (it only fetches `${ISSUER}/.well-known/openid-configuration` when a desktop client actually attempts an OAuth flow), so the api container boots fine even when `fixture-idp` is not in the active profile — DNS resolution failure occurs only on demand.

## D-02 verification — fixture-idp accepts ANY client credentials

Per CONTEXT D-02, the executor MUST verify what fixture-idp accepts (do not guess). Direct read of `tests/fixtures/idp/server.mjs:84-105`:

```javascript
if (path === "/token" && req.method === "POST") {
  return json(res, {
    access_token: "fixture-access-token",
    token_type: "Bearer",
    expires_in: 3600,
    id_token: "..." // hardcoded JWT, aud: "fixture-client"
    scope: "openid email profile",
  });
}
```

There is **no `client_id` / `client_secret` validation** — any value passed is accepted. The `id_token`'s `aud` claim is hardcoded to `"fixture-client"`, but Better Auth's genericOAuth does not enforce `aud === client_id` mismatch by default. Therefore the literal default values (`conformance-test-client` / `conformance-test-secret-do-not-use-in-prod`) are documentation-grade only.

## Rule-3 deviation — `.env` empty-vs-unset under docker-compose v2.23

**Found during:** First post-fix run of `oidc-env-wiring.test.ts` (3/4 still RED after the docker-compose.yml edit).

**Issue:** `docker compose --profile default --profile contract-test config` rendered `OIDC_ISSUER_URL: ""` instead of the substituted default. Investigation traced to `.env` declaring `OIDC_ISSUER_URL=` (empty string) — docker-compose v2.23 treats empty `.env` values as "set" for `${VAR:-default}` substitution purposes, blocking the default from applying. (POSIX shell `:-` would treat empty as unset; docker-compose v2.x does not.)

**Fix:** Removed the three empty OIDC_ assignments from both `.env.example` and the bootstrap-generated `.env`. Documented operator-override pattern with example values in the new `.env.example` block. After re-running `tools/bootstrap.sh`, the regenerated `.env` no longer ships empty OIDC_ keys, so `${VAR:-default}` resolves to the compose-side default cleanly.

**Files modified beyond CONTEXT scope:** `.env.example` (1 block) — required to unblock the contract-tested behavior. Tracked here as a deviation per Rule 3 (auto-fix blocking issues).
