## Summary

Phase 07.1 turns the two UI-SPEC documents from Phase 07 into a working Next.js 15 App Router application at `apps/web/`. CONTEXT.md locks every meaningful choice (stack pins, deploy topology, admin gating, testing depth, security headers, project layout, CI shape) — this research only fills in *how* to wire them up correctly inside the existing repo. The two highest-risk integration points are (a) Better Auth session validation across the RSC + middleware + Client boundary, and (b) deterministically producing the four UI-states (`loading / empty / error / success`) per screen in Playwright against the real docker-compose stack.

The repo already runs Traefik v3.6 with a file-provider dynamic config at `compose/traefik/dynamic.yml`, Playwright 1.59.1 is installed at root, Better Auth pinned to **1.6.9** (CONTEXT D-STACK-5 — note: the original prompt mentioned 1.6.10; CONTEXT and `apps/api/package.json` both say 1.6.9, so 1.6.9 wins). pnpm 11.0.8 + Node 24 workspace is in place, `apps/*` is already in `pnpm-workspace.yaml`, and `.github/workflows/ci.yml` shows the canonical step-security/harden-runner + pnpm/action-setup style to mirror in `.github/workflows/web.yml`.

**Primary recommendation:** Scaffold `apps/web/` with `pnpm dlx create-next-app@latest --ts --tailwind --eslint --app --src-dir --import-alias "@/*"`, then immediately delete the generated ESLint config (the repo uses Biome — see `package.json: lint` script), wire `next.config.ts` to `output: 'standalone'` + `headers()`, run `pnpm dlx shadcn@latest init` with components.json pointing at `apps/web/src/components/ui`, and follow the route-group + middleware patterns documented below.

### Pattern 1: Server/Client boundary per screen

The screens divide into three clean buckets:

| Bucket | Screens | Rendering |
|--------|---------|-----------|
| Public form (no fetch) | U1, U2 | `'use client'` page; react-hook-form + zod local state; submit calls `authClient.signIn.email()` |
| Public one-shot mutation | U3 | RSC reads `searchParams.token`; delegates to `<VerifyEmailClient token={token} />` (Client) that fires `authClient.verifyEmail()` on mount |
| Authenticated fetch | U4–U13, A3 | RSC `page.tsx` calls `getQueryClient().prefetchQuery(...)`, wraps tree in `<HydrationBoundary state={dehydrate(...)}>`; Client child uses `useQuery` |
| Static link grid | A2 | Pure RSC; reads `process.env.NEXT_PUBLIC_GRAFANA_BASE_URL` at build time |
| Auth-gated layout | `(auth)/layout.tsx` | RSC; `await auth.api.getSession({ headers: await headers() })`; `redirect('/sign-in')` on null |

**Critical rule:** `'use client'` only on leaf components that need state/effects. `page.tsx` for fetching screens stays RSC and prefetches via TanStack Query 5's RSC hydration helper. [CITED: tanstack.com/query/v5/docs/framework/react/guides/advanced-ssr]

### Pattern 2: Better Auth — server-side session validation

```tsx
// apps/web/src/lib/auth-server.ts
import { headers } from 'next/headers';
import { auth } from '@openwhispr/auth/server'; // re-export of the existing apps/api auth instance

export async function getServerSession() {
  return await auth.api.getSession({ headers: await headers() });
}

// apps/web/src/app/(auth)/layout.tsx
import { redirect } from 'next/navigation';
import { getServerSession } from '@/lib/auth-server';

export default async function AuthLayout({ children }: { children: React.ReactNode }) {
  const session = await getServerSession();
  if (!session) redirect('/sign-in');
  return <AppShell user={session.user}>{children}</AppShell>;
}
```

[CITED: better-auth.com/docs/integrations/next — `auth.api.getSession({ headers })` is the canonical RSC pattern]

**Open issue verified:** better-auth/better-auth#7008 reports `getSession()` returning null when cookie cache is enabled in Next.js App Router RSC. Mitigation: do not enable Better Auth's cookie cache option in `apps/api/src/auth.ts` (it is not enabled today — verified in `apps/api/src/auth.ts:80-95`). [VERIFIED: github.com/better-auth/better-auth/issues/7008]

### Pattern 4: middleware.ts — cookie presence gate

```ts
// apps/web/src/middleware.ts
import { NextResponse, type NextRequest } from 'next/server';
import { getSessionCookie } from 'better-auth/cookies';

export function middleware(req: NextRequest) {
  const cookie = getSessionCookie(req); // CHECKS EXISTENCE ONLY — does not validate
  if (!cookie) {
    const url = req.nextUrl.clone();
    url.pathname = '/sign-in';
    return NextResponse.redirect(url);
  }
  return NextResponse.next();
}

export const config = {
  matcher: ['/app/:path*'], // (auth) group only; (public) + (admin) bypass
};
```

**Security note:** `getSessionCookie` checks existence ONLY. Real validation happens in `(auth)/layout.tsx` via `auth.api.getSession`. This two-layer pattern is what Better Auth recommends. [VERIFIED: better-auth/better-auth#2233 + better-auth.com/docs/integrations/next — "optimistic redirect in middleware, real validation in layout"]

**Admin matcher:** intentionally absent — admin gating is Traefik basic-auth (D-ADMIN-1), not application-layer.

### Pattern 5: TanStack Query 5 — RSC prefetch + Client hydrate

```tsx
// apps/web/src/lib/query-client.ts
'use client';
import { QueryClient, QueryClientProvider } from '@tanstack/react-query';
import { useState } from 'react';

export function QueryProvider({ children }: { children: React.ReactNode }) {
  const [client] = useState(() => new QueryClient({
    defaultOptions: { queries: { staleTime: 60_000, refetchOnWindowFocus: false } },
  }));
  return <QueryClientProvider client={client}>{children}</QueryClientProvider>;
}

// apps/web/src/app/(auth)/app/page.tsx — RSC
import { dehydrate, HydrationBoundary } from '@tanstack/react-query';
import { makeServerQueryClient } from '@/lib/query-client-server';
import { queryKeys } from '@/lib/query-keys';
import { UsageDashboardClient } from '@/components/screens/usage/UsageDashboardClient';

export default async function UsagePage() {
  const qc = makeServerQueryClient();
  await qc.prefetchQuery({
    queryKey: queryKeys.usage(),
    queryFn: () => fetch('/api/usage', { headers: await forwardCookies() }).then(r => r.json()),
  });
  return (
    <HydrationBoundary state={dehydrate(qc)}>
      <UsageDashboardClient />
    </HydrationBoundary>
  );
}
```

### Pattern 6: i18next App Router (no `next-i18next`)

**Server instance** — created per request, never reused across requests:

```ts
// apps/web/src/lib/i18n.ts
import { createInstance, type i18n } from 'i18next';
import resourcesToBackend from 'i18next-resources-to-backend';

export async function getServerI18n(lng: string, ns: string[]): Promise<i18n> {
  const i = createInstance();
  await i
    .use(resourcesToBackend((language: string, namespace: string) =>
      import(`@/locales/${language}/${namespace}.json`)
    ))
    .init({ lng, fallbackLng: 'en', ns, defaultNS: 'common', interpolation: { escapeValue: false } });
  return i;
}
```

**Client provider** — receives the dictionary as a serialized prop from the nearest RSC parent, never re-fetches:

```tsx
// apps/web/src/lib/i18n-client.tsx
'use client';
import { I18nextProvider } from 'react-i18next';
import { createInstance } from 'i18next';
import { useMemo } from 'react';

export function I18nProvider({ lng, resources, children }: { lng: string; resources: Record<string, Record<string, unknown>>; children: React.ReactNode }) {
  const i18n = useMemo(() => {
    const i = createInstance();
    i.init({ lng, resources: { [lng]: resources }, ns: Object.keys(resources), defaultNS: 'common', interpolation: { escapeValue: false } });
    return i;
  }, [lng, resources]);
  return <I18nextProvider i18n={i18n}>{children}</I18nextProvider>;
}
```

**Middleware locale negotiation** — read `NEXT_LOCALE` cookie → fallback to `Accept-Language` → fallback to `en`. v1 ships `en` only, so the negotiation chain currently always returns `en`. Code lives in `middleware.ts`; details deferred to Phase 10. [CITED: locize.com/blog/i18n-next-app-router]

**Anti-pattern:** Do NOT install `next-i18next` (Pages-Router only, breaks under App Router). [CITED: github.com/i18next/next-i18next README explicitly says Pages Router]

## Common Pitfalls

### Pitfall 1: RSC + Client component prop serialization
**What goes wrong:** Passing non-serializable values (functions, class instances, Dates) from RSC `page.tsx` to a Client child throws at render. The i18n provider expects a `resources` object — must serialize cleanly.
**Prevention:** Stick to `string | number | boolean | array | plain object` across RSC→Client boundaries. Pass session as `{ id, email, name, emailVerified, createdAt: string }` not the raw Better Auth object (which contains methods).
**Warning sign:** Build error `Error: Functions cannot be passed directly to Client Components`.

### Pitfall 2: Better Auth cookies not forwarded in RSC fetch
**What goes wrong:** `fetch('/api/usage')` inside an RSC does NOT automatically include browser cookies — RSC runs server-side and must explicitly forward them.
**Prevention:** Use `import { headers } from 'next/headers'` and forward the `cookie` header:
```ts
const cookieHeader = (await headers()).get('cookie') ?? '';
await fetch(`${process.env.INTERNAL_API_URL}/api/usage`, { headers: { cookie: cookieHeader } });
```
**Warning sign:** RSC `prefetchQuery` returns 401 while the same endpoint works from the Client.

### Pitfall 3: Middleware runs on Edge by default (Node modules don't work)
**What goes wrong:** Importing `better-auth/server` or Drizzle in `middleware.ts` breaks under Edge runtime.
**Prevention:** Either (a) keep middleware to cookie existence check only via `getSessionCookie` (which is Edge-safe), OR (b) opt into Node runtime with `export const runtime = 'nodejs'` (available since Next.js 15.2). For 07.1, (a) is the pattern.
**Warning sign:** `Module not found: Can't resolve 'fs'` during build. [VERIFIED: next-auth.js docs + better-auth#2233]

### Pitfall 4: Hydration mismatch with TanStack Query SSR
**What goes wrong:** Server renders empty state, client immediately fetches and renders populated state → mismatch warning.
**Prevention:** Use `HydrationBoundary` + server-side `prefetchQuery` so the dehydrated state on the wire matches what the client renders on first paint.
**Warning sign:** Console warning `Hydration failed because the initial UI does not match what was rendered on the server`.

### Pitfall 5: `route.fulfill()` masks real backend behavior in `success` state
**What goes wrong:** Tempting to use `page.route()` for ALL four states. CONTEXT D-TEST-3 forbids this — `success`/`empty` must use seeded real data.
**Prevention:** Reserve `route()` for `loading` (use `route.continue({ delay })`) and `error` (use `route.fulfill({ status: 500 })`). For `empty`, seed nothing. For `success`, seed via API calls in a fixture.
**Warning sign:** PR reviewer flags a `route.fulfill({ status: 200, json: { ... } })` in a `success` spec.

### Pitfall 6: Tailwind 4 utility names changed
**What goes wrong:** Copy-pasted Tailwind 3 utility names like `text-zinc-900/50` may not match Tailwind 4 token names.
**Prevention:** Use the `@theme` token names defined in `globals.css` (e.g., `text-text`, `bg-panel`). Hex literals and OKLCH work too.
**Warning sign:** Class appears in HTML but no styles applied.

### Pitfall 7: shadcn/ui v2 + RSC `'use client'` placement
**What goes wrong:** Some shadcn primitives (`Form`, `DropdownMenu`, `AlertDialog`, `Tooltip`) require client-side React and ship with `'use client'` at the top. Importing them into an RSC implicitly creates a Client subtree.
**Prevention:** Accept the boundary at the import point — that's how shadcn is designed. The RSC wrapper above renders the children server-side; only the interactive primitive becomes a Client island.
**Warning sign:** Bundle analyzer shows large `__use_client__` chunks under what you expected to be a static page.

### Pitfall 8: Better Auth React `useSession()` shape under React 19
**What goes wrong:** Older blog posts show `useSession()` returning `{ data, isLoading }`. Better Auth 1.6 returns `{ data, isPending, error, refetch }` — `isLoading` does not exist.
**Prevention:** Type-check via Better Auth's exported types; the field is `isPending`.
**Warning sign:** Skeleton never disappears because `isLoading` is always `undefined`.
[VERIFIED: A8 in `.planning/phases/07-frontend-ui-spec/UI-SPEC-admin.md` Assumptions Resolved table]

### Pitfall 9: CSP `connect-src 'self'` blocks Better Auth dev tools
**What goes wrong:** Strict CSP on auth pages blocks `connect-src` to anything other than self; in dev this is fine, but if any analytics or upstream is added later, the strict CSP silently breaks it.
**Prevention:** Keep auth-page CSP strict (D-SEC-1) but document that any future external integration requires CSP review.
**Warning sign:** Network panel shows blocked requests with `Refused to connect` errors.

### Pitfall 10: Standalone output + workspace dependencies
**What goes wrong:** `output: 'standalone'` tracks file deps via `@vercel/nft`; pnpm workspace symlinks can confuse the tracer, producing a Docker image missing `@openwhispr/wire-schemas`.
**Prevention:** Set `outputFileTracingRoot: path.join(__dirname, '../../')` in `next.config.ts` so the tracer walks the monorepo. [CITED: nextjs.org/docs/app/api-reference/next-config-js/output]
**Warning sign:** Container starts then crashes with `Cannot find module '@openwhispr/wire-schemas'`.

### `compose/traefik/dynamic.yml` patch

Append to the `http.routers` block (alongside existing `api`, `grafana`, etc.):

```yaml
    web:
      rule: "Host(`api.localhost`) && PathPrefix(`/`)"
      service: web-svc
      entryPoints: [websecure]
      priority: 1                          # lower than `api` (default 50) — api wins on /api/*
      tls: {}
    web-admin:
      rule: "Host(`api.localhost`) && PathPrefix(`/admin`)"
      service: web-svc
      entryPoints: [websecure]
      priority: 100                        # higher than `web` so admin matches first
      middlewares: [admin-basicauth]
      tls: {}
```

…and to `http.services`:

```yaml
    web-svc:
      loadBalancer:
        servers:
          - url: "http://web:3000"
```

…and to `http.middlewares` (new top-level section if absent):

```yaml
  middlewares:
    admin-basicauth:
      basicAuth:
        users: []                          # populated at boot by an init step that reads ADMIN_BASIC_AUTH_USERS
```

**Routing note:** Traefik picks the longer `PathPrefix` first when priorities tie; setting `priority: 100` on `web-admin` makes the precedence explicit so `/admin/*` always hits the basic-auth chain before falling through to plain `web`. Existing `api` router has `Host(\`api.localhost\`)` rule with default priority — its more specific Host+PathPrefix matchers already win for `/api/*`. Verify by inspection during plan-phase. [VERIFIED: existing `compose/traefik/dynamic.yml` shows `api` already binds `Host(\`api.localhost\`)`]

**Operator surface for `admin-basicauth.users`:** Two viable encodings:
1. Bake users into `dynamic.yml` at deploy time via `envsubst` before mounting (current repo doesn't have this — would need a new compose init script).
2. Switch the admin middleware to label-based on the compose service itself (`labels: traefik.http.middlewares.admin-basicauth.basicauth.users=...`).

CONTEXT D-ADMIN-1 says "Traefik labels-based middleware". Option (2) wins. Move the `admin-basicauth` middleware definition OUT of `dynamic.yml` and INTO the `web` service's labels — caveat: the existing repo uses `providers.file` only (no docker provider in `traefik.yml:providers`). To use labels, the docker provider must be added. **The planner must decide between adding the docker provider OR using `envsubst` against `dynamic.yml`.** Recommendation: prefer labels + add docker provider (one-line in `traefik.yml`); the docker provider is officially supported alongside file. ## Slice Ordering / Wave Breakdown

**Constraint:** `(auth)/layout.tsx` redirects unauthenticated users to `/sign-in`, so any test against `/app/**` requires a working auth path. Auth slice MUST come first.

**Recommended wave structure** (planner can adjust within deps):

| Wave | Slices | depends_on | Rationale |
|------|--------|-----------|-----------|
| 0 | Scaffold + Infra: `apps/web/` skeleton, `next.config.ts`, Dockerfile, compose `web` service, Traefik labels, root layout, providers (QueryProvider/I18nProvider), `app/api/health/route.ts`, `globals.css` + Tailwind 4 tokens, shadcn init + add-all, vitest+playwright bootstraps, lefthook entry, `web.yml` skeleton | — | Nothing renders without this; verify infra alone via curl/health |
| 1 | Auth slice: U1 sign-in + U2 sign-up + U3 verify-email + `middleware.ts` + `(auth)/layout.tsx` session guard | Wave 0 | Unlocks every authenticated screen for testing |
| 2 (parallel) | Account+Usage slice: U5 + U4 (KPI-only) | Wave 1 | Smallest authenticated screens; high test coverage signal |
| 2 (parallel) | Admin slice: A2 (static cards) + A3 (config view) | Wave 0 (NOT Wave 1 — admin is Traefik-gated, no app-level session check) | Can proceed in parallel with the end-user surface |
| 3 (parallel) | Transcriptions slice: U6 list + U7 detail | Wave 1 | Establishes the list+detail pattern reused below |
| 3 (parallel) | Notes slice: U8 list + U9 detail + U10 search | Wave 1, Wave 3-trx (for pattern reuse not hard dep) | Adds search screen pattern |
| 4 | Conversations slice: U11 list + U12 detail + U13 search | Wave 3 patterns | Final repeat; pure pattern application |
| 5 | Polish & verify: bundle-budget tuning, perf budgets doc (`perf-budgets.md`), CI green, lefthook green | All previous | Verification gate |

**Why admin parallel to auth:** A2 calls zero endpoints (pure static cards from `NEXT_PUBLIC_*` env), and A3 uses session-cookie auth but the admin layout has no app-level check (D-ADMIN-1). Operator testing of A2/A3 uses a Traefik basic-auth + a seeded user — both achievable from Wave 0 infra.

**Why split end-user slices vertically:** Each slice ships an RSC page + Client child + queries + i18n keys + vitest unit tests + Playwright e2e × 5 (loading/empty/error/success + axe) in one atomic batch. Vertical slices minimize integration risk vs horizontal "all RSC then all clients then all tests."

### Known Threat Patterns for Next.js 15 + React 19 + Better Auth

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| XSS via uncontrolled `dangerouslySetInnerHTML` | Tampering | Never use in this codebase; ESLint/Biome rule banned. Copy keys are i18next strings (no HTML). |
