# Phase 07.1: Web App Implementation - Context

**Gathered:** 2026-05-12
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 07.1 turns the two UI-SPEC markdown documents produced in Phase 7 into a working Next.js 15 + React 19 + Tailwind 4 + shadcn/ui v2 application at `apps/web/`. Every screen enumerated in `UI-SPEC-admin.md` (A2, A3) and `UI-SPEC-end-user.md` (U1–U13) is implemented at the route paths the spec names. The app is deployed same-origin behind the existing Traefik proxy alongside `apps/api`. Playwright e2e covers all four UI states per screen plus a WCAG 2.2 AA axe-core scan. Coverage gates and TDD discipline carry over from CLAUDE.md.

This phase exists because the originating Phase 7 was scoped to "spec only" via a planner-side recommendation that the user disagreed with after the fact. Phase 07.1 closes the gap.

</domain>

<decisions>
## Implementation Decisions (locked by user 2026-05-12)

### Deploy topology

- **D-DEPLOY-1 — Same-origin under Traefik.** `apps/web` runs as a docker-compose service `web` (Next.js production server `next start`). Traefik routes `/` → web and `/api/*` → api. Cookies/CORS are not an issue. No Vercel deployment in v1.
- **D-DEPLOY-2 — `web` Dockerfile.** Multi-stage build (deps → build → runner) using `node:24-alpine`. Standalone output (`output: 'standalone'` in `next.config.ts`) so the runtime image is ~150MB. Health endpoint `/api/health` (renders a server component that returns OK) for compose healthcheck.

### Admin gate

- **D-ADMIN-1 — Traefik basic-auth on /admin/*.** ENV `ADMIN_BASIC_AUTH_USERS` (htpasswd-format `user:hash` comma-separated) consumed by a Traefik labels-based middleware on the web service's `/admin` PathPrefix. Web does not implement application-level role checks — auth is resolved at the edge. This honors Phase 7 A4 refutation (Better Auth v1.6.9 has no `role` column) without introducing a schema migration.
- **D-ADMIN-2 — First-registered-user convention is documentation-only.** No code path treats the first registered user differently; operators add their email-derived basic-auth credentials via env. Reference docs (Appendix A in this CONTEXT) describe the convention.

### Testing depth

- **D-TEST-1 — Full UI-state matrix per Playwright screen.** Each of the 15 screens is tested against all 4 states declared in its UI-SPEC States subsection: `loading`, `empty`, `error`, `success`. Plus 1 axe-core WCAG 2.2 AA scan per screen via `@axe-core/playwright` with `withTags(['wcag22aa'])`. ≈ 75 Playwright tests total.
- **D-TEST-2 — Strict TDD per CLAUDE.md.** RED test before every component, hook, or util. Coverage ≥ 90/90/90/90 on diff (lines/branches/functions/statements). Applies uniformly — no presentational-vs-logic carve-out.
- **D-TEST-3 — Real services via docker-compose, not mocks.** Playwright runs against `docker compose up api postgres valkey traefik web` plus Better Auth wired in. State fixtures use network interception (Playwright's `route()`) ONLY for `loading` and `error` states where the real backend would not naturally produce them deterministically; `empty` and `success` use seeded real data.
- **D-TEST-4 — Vitest + @testing-library/react for unit/component layer.** RSC components tested with the standard React 19 + `node` test environment (Server Components rendered via `renderToString` or extracted into Client Components for testability). No internal-logic mocks; only fs / network / time boundaries may be stubbed.

### Tech stack pins (carried from UI-SPEC + RESEARCH)

- **D-STACK-1 — Next.js 15.x, React 19.2, TypeScript strict, Tailwind 4.x.** No Pages Router. App Router only. RSC by default; `'use client'` only where state/effects require it.
- **D-STACK-2 — shadcn/ui v2 (copy-into-repo).** Install via `pnpm dlx shadcn@latest init` then add primitives per UI-SPEC Appendix E inventory. `components.json` lives at `apps/web/components.json`.
- **D-STACK-3 — TanStack Query 5 for client data fetching, TanStack Table 8 for tables.** Query keys factored per screen as documented in UI-SPEC Conventions.
- **D-STACK-4 — react-hook-form 7 + zod 4.** Zod schemas imported from `packages/wire-schemas` where the API surface defines them; UI-specific schemas live in `apps/web/src/lib/schemas/`.
- **D-STACK-5 — better-auth/react 1.6.9.** Uses the same Better Auth installation as `apps/api`. `useSession()` for client components; server-side `getSession()` in middleware and RSC.
- **D-STACK-6 — Recharts 3.8 deferred.** Phase 7 Plan 01 refuted the U4 daily-series + provider-breakdown assumptions; U4 collapses to KPI cards only (Card primitives, no chart library). Recharts not installed in this phase.
- **D-STACK-7 — i18next + react-i18next, App-Router compatible.** `next-i18next` is NOT used (Pages-Router only). Bundles at `apps/web/src/locales/en/{admin,end-user,common}.json`. Locale negotiation chain: `Accept-Language` → cookie `NEXT_LOCALE` → user preference (deferred until Phase 10 — v1 ships `en` only).
- **D-STACK-8 — date-fns for date handling.**

### Bundle / perf budgets

- **D-PERF-1 — Bundle budget per route ≤ 200KB gzipped.** Enforced by `size-limit` + `@next/bundle-analyzer`. CI gate fails the build if exceeded.
- **D-PERF-2 — LCP < 2.5s, INP < 200ms.** Measured by a Playwright perf script using `getEntriesByType('navigation')` against `localhost` simulated 4G; documented per-route in `apps/web/perf-budgets.md`. Not a hard CI gate in this phase — informational floor.

### Security headers

- **D-SEC-1 — CSP, HSTS, X-Frame-Options DENY, Referrer-Policy, Permissions-Policy.** All set via `next.config.ts` `headers()` function. Auth pages (`/sign-in`, `/sign-up`, `/verify-email`) get a stricter CSP that excludes all third-party origins per UI-SPEC Constraints.
- **D-SEC-2 — No tokens or sensitive payloads in localStorage.** Session lives in Better Auth HttpOnly cookies exclusively.

### Project structure

- **D-STRUCT-1 — App Router layout.**
  ```
  apps/web/
    src/
      app/
        (public)/sign-in/page.tsx, sign-up/page.tsx, verify-email/page.tsx
        (auth)/app/page.tsx, account/page.tsx, transcriptions/...
        (admin)/admin/observability/page.tsx, config/page.tsx
        api/health/route.ts
        layout.tsx, globals.css
      components/
        ui/  (shadcn primitives, copy-into-repo)
        screens/  (per-screen composites that page.tsx imports)
      lib/
        auth-client.ts, query-client.ts, i18n.ts, schemas/, query-keys.ts
      locales/en/{admin,end-user,common}.json
    public/
    next.config.ts, tsconfig.json, package.json, components.json, .env.example
  ```
- **D-STRUCT-2 — `pnpm-workspace.yaml` already includes `apps/*`.** No workspace plumbing change needed.

### CI / lefthook

- **D-CI-1 — Single GHA workflow `.github/workflows/web.yml`.** Jobs: typecheck → vitest (unit/component) → build → size-limit → Playwright (against docker-compose). Triggers: `apps/web/**`, `packages/wire-schemas/**`, `apps/api/src/routes/**` (since e2e exercises the API).
- **D-CI-2 — lefthook web hook.** Pre-commit runs `pnpm --filter web typecheck` and `pnpm --filter web lint` on staged `apps/web/**` files. Pre-push runs the full vitest suite.

<code_context>
## Existing Code Insights

### Reusable Assets
- **`packages/wire-schemas`**: zod schemas for the API surface; web imports these for fetch result validation.
- **`packages/auth`**: Better Auth shared package (server uses it via apps/api/src/auth.ts; web uses better-auth/react client which reads the same session cookie).
- **`packages/i18n`**: server-side i18next setup; web mirrors the same locale-bundle convention.
- **`apps/api/src/routes/better-auth-handler.ts`**: catch-all that serves every Better Auth endpoint web calls — no per-path changes needed in api for web to work.

### Established Patterns
- **English-only source.** Code, comments, identifiers, copy-key names — all English. Visible strings carry copy keys (see UI-SPEC for keys). Russian translations land in Phase 10.
- **Atomic commits.** Each task ends with a single commit; tests + implementation in the same commit.
- **No emojis in source.**

### Integration Points
- **Traefik already terminates TLS** and handles `/api/*` → api. Adding web is one new service + one new router (`/` → web) + one new middleware (basic-auth on `/admin`).
- **Better Auth session cookies are SameSite=Lax HttpOnly** — same-origin deploy means no cookie surgery.
- **Postgres + Valkey already wired** for api. Web reads nothing from them directly; it goes through api.

## Specific Ideas

- **MVP mode.** This phase uses vertical-slice planning: each slice is a feature (auth flow / account / transcriptions / notes / conversations / admin) implemented end-to-end (RSC route + Client Component + queries + TDD + e2e) before moving to the next.

- **Three design-gap markers from Phase 7 are implementation hints.** U1 disabled-forgot-password, A3 layout after env-block removal, U4 KPI-only layout — each needs a deliberate visual decision during implementation. Treat the HTML `DESIGN-GAP` comments in UI-SPEC files as instructions: the executor proposes a visual; if it's clearly wrong an operator can swap it. No new Claude Design call required for v1.
