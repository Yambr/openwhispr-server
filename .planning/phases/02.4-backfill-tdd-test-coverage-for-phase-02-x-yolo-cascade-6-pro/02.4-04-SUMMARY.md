## Decisions Made

- **postgres:17.5-alpine** (not 17-bookworm): the actual `docker-compose.yml` `postgres:` service pin is `17-bookworm` per plan body but the deployed compose file uses `17.5-alpine`. Test exercises the same image operators run.
- **Rotating superuser password helper** (`applyTemplate` + `currentOwnerPw` + `superUri()`): the SQL template ALTERs the owner's password every apply, which invalidates the static URI returned by `container.getConnectionUri()`. Rebuilding the URI per call is cheaper than reseeding the container.

**2. [Rule 3 - Blocking] Vitest 4 removed three-arg `describe(name, fn, opts)` signature**

- **Found during:** Task 1 (first vitest run)
- **Issue:** Plan example used `describe("...", () => { ... }, { timeout: 120_000 })`. Vitest 4 throws `TypeError: Signature "test(name, fn, { ... })" was deprecated in Vitest 3 and removed in Vitest 4. Please, provide options as a second argument instead.`
- **Fix:** Switched to `describe("...", { timeout: 120_000 }, () => { ... })`.
- **Files modified:** `tests/integration/postgres-roles-idempotent.test.ts`
- **Verification:** Suite parses and executes; previously aborted at module load.
- **Committed in:** `76583d1`

**3. [Rule 1 - Bug] Plan example assumed `getConnectionUri()` stays valid after the script ALTERs the owner password**

- **Found during:** Task 1 (second vitest run)
- **Issue:** First apply ran successfully in `beforeAll`, but every subsequent query failed with `28P01 password authentication failed for user "openwhispr_owner"` because `superuserUri` (captured from `getConnectionUri()`) embedded the original `initial_owner_pw` while the script had ALTERed the password to `owner_pw_v1`. The "ALTER branch took effect" test had the same issue for the app role.
- **Fix:** Introduced `currentOwnerPw` closure variable, `superUri()` helper that rebuilds the URI from container host/port plus the current password, and `applyTemplate(ownerPw, appPw)` that runs the script with the live credential then rotates `currentOwnerPw`. Seeded the container with `withPassword("owner_pw_v1")` so the very first apply (which ALTERs to `owner_pw_v1`) is a no-op on the password and the URI stays valid mid-apply.
- **Files modified:** `tests/integration/postgres-roles-idempotent.test.ts`
- **Verification:** All 6 tests now exercise the live credential; no `28P01` errors.
- **Committed in:** `76583d1`

**4. [Rule 1 - Bug] `pg.Client.connect()` resolves to the Client, not undefined**

- **Found during:** Task 1 (post-fix run, 5/6 passing)
- **Issue:** Plan example used `await expect(client.connect()).resolves.toBeUndefined()`, but pg 8.20 resolves with the Client instance. Test failed with `expected Client{...} to be undefined`.
- **Fix:** Changed to `await expect(client.connect()).resolves.toBeDefined()` and added an explicit `SELECT current_user` assertion confirming the connection authenticated as `openwhispr_app` — proves the new password took effect.
- **Files modified:** `tests/integration/postgres-roles-idempotent.test.ts`
- **Verification:** 6/6 tests green.
- **Committed in:** `76583d1`
