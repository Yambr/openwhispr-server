# Phase 08.4: realtime-ws proxy forwarding fix — Research

**Researched:** 2026-05-13
**Domain:** k6 WebSocket client / Fastify WS upgrade auth / @fastify/http-proxy v11 frame forwarding
**Confidence:** HIGH on top hypothesis (H7 — new); MEDIUM-HIGH on recommended fix
**Phase:** 08.4 — `realtime-ws-proxy-forwarding-fix`
**Depends on:** Phase 08.3 (CLOSED partial — mock-litellm echo handler shipped, Run 4 plateau)
**Requirements:** SCALE-02, TEST-LOAD-01

## Summary

The `realtime_ws_roundtrip_ms` Trend is empty NOT because `@fastify/http-proxy` v11 fails to forward upstream→client frames, but because **the k6 load-test client never sends the upstream-bound `session.update` frame in the first place**. The k6 adapter at `tools/load-test/src/utils/http-client.ts:152-154` constructs `new W(url, params)` — TWO arguments — while `k6/websockets` requires `new WebSocket(url, protocols, params)` — THREE arguments. With the 2-arg call, k6 binds our `{ headers: { authorization: 'Bearer …' }, tags: { endpoint: 'realtime-ws' } }` to the **`protocols`** slot (silently coerced/dropped) and `params` is `undefined`. Net effect: the WS upgrade leaves the k6 VU **with no `Authorization: Bearer …` header**, the api's `dualAuthHook` throws `AuthError("unauthorized")` BEFORE the proxy upgrade fires, api emits a 401 HTTP response, k6 reports a failed upgrade — no `open` event, no `send()`, no inbound frame, no `realtime_ws_roundtrip_ms` data points. The Run 4 metrics back this up: `ws_sessions=168 836` (each `client.ws()` callback counted), `ws_connecting p95=5.5ms` (fast 401 over TLS), **but NO `ws_msgs_sent` or `ws_msgs_received` line in the k6 summary at all** — the smoking gun for "open never fired."

The `@fastify/http-proxy` v11 source confirms it DOES forward target→source frames bidirectionally (`index.js:131-140`, `proxyWebSockets`). The `apps/api/src/routes/realtime.ts` integration test (`realtime.test.ts:264-308`) successfully proves the upstream receives the right URL + headers — but it uses Node's `ws` library client (which DOES respect a `headers` option), masking the k6-side bug. The vitest mock for the flow (`realtime-ws.test.ts`-style mocks) injects synthetic events into a mocked socket, bypassing the constructor entirely. The bug is invisible in both test surfaces and only manifests under real k6.

**Primary recommendation:** Fix the k6 adapter to use the correct 3-arg constructor (`new W(url, null, params)`). Add a focused integration test that asserts `params.headers` reach a real upstream upgrade. Re-run smoke + 30-min plateau and expect `realtime_ws_roundtrip_ms` to populate.

**Secondary recommendation:** Once fix lands, verify that `@fastify/http-proxy` v11's bidirectional frame forwarding works end-to-end through the real api+mock-litellm stack with an explicit smoke check (one VU, one round-trip, asserted in run log). This closes the loop on the historical "did the proxy ever work" doubt without rewriting the route.

## Hypothesis scoring

Six brief-supplied hypotheses (H1–H6) plus one new hypothesis (H7) discovered during code-source analysis.

### H1 — `@fastify/http-proxy` v11 prefix-rewrite chops the upgrade path

**Status:** REJECTED.

`@fastify/http-proxy@11.4.4/index.js:438-459` (`findUpstream`) is the authoritative path-derivation site. With `wsUpstream='ws://litellm:4000'` and `dest='/v1/realtime'`, it computes `new URL('/v1/realtime', 'ws://litellm:4000')` → `ws://litellm:4000/v1/realtime`. With `prefix='/v1/realtime'` and `rewritePrefix='/v1/realtime'`, `fromParameters` (lines 592-619) strips the prefix from `request.url` then re-prepends the rewritePrefix — net no change. The upstream sees `GET /v1/realtime?user=<id>`. mock-litellm registers `app.get('/v1/realtime', {websocket:true}, ...)` which matches path-exactly regardless of query string (Fastify routes match path, query is opaque to the router). Path is correct.

Furthermore — the apps/api integration test `apps/api/src/routes/realtime.test.ts:264-308` ASSERTS upstream path is `/v1/realtime` with `?user=<TEST_USER>`. Test is GREEN. Path is empirically verified.

### H2 — preHandler mutates `req.raw.url` after http-proxy snapshots the URL

**Status:** REJECTED.

`@fastify/http-proxy/index.js:621-635` shows the `handler` function reading `request.url` (which proxies to `req.raw.url` via Fastify's request getter) at handler-time. preHandler runs BEFORE handler in Fastify's lifecycle (`onRequest → preParsing → preValidation → preHandler → handler`). The mutation in `apps/api/src/routes/realtime.ts:170` (`req.raw.url = u.pathname + u.search`) lands BEFORE `handler` reads `request.url`. Empirically: the realtime.test.ts test at line 310-332 ("overwrites a caller-supplied ?user=") proves the mutation does land on the upstream URL.

### H3 — `wsClientOptions.rewriteRequestHeaders` returns headers mock-litellm rejects

**Status:** REJECTED.

`buildRewriteRequestHeaders` (`apps/api/src/routes/realtime.ts:52-71`) returns a clean headers object with `authorization: Bearer ${masterKey}` and `x-litellm-spend-logs-metadata`. It does NOT touch `sec-websocket-*` headers — those are added by the `ws` library itself when constructing `new WebSocket(url, subprotocols, optionsWs)` (`index.js:477`). The `ws` library generates a fresh `sec-websocket-key` per connection. mock-litellm uses `@fastify/websocket` which delegates to the same `ws` library on the server side — fully compatible. The realtime.test.ts assertion at line 284-286 confirms the master-key swap reaches the real upstream.

### H4 — Upstream-initiated frames don't propagate through @fastify/http-proxy v11

**Status:** REJECTED with source citation.

`@fastify/http-proxy@11.4.4/index.js:94-160` (`proxyWebSockets`, used when `wsReconnect:false`) wires BOTH directions:
- `source.on('message', (data, binary) => { … target.send(data, { binary }) })` (lines 110-119) — client→upstream
- `target.on('message', (data, binary) => { … source.send(data, { binary }) })` (lines 131-140) — upstream→client

The library is healthy on this code path. v11.4.4 was published 2025-Q2 and the `proxyWebSockets` function is unchanged from v11.0.0. No open GitHub issues at https://github.com/fastify/fastify-http-proxy/issues describe a frame-forwarding regression in 11.x.

### H5 — `wsReconnect: false` causes the proxy to close upstream socket prematurely

**Status:** REJECTED.

The `close` callback (lines 96-108) is only invoked on `source.close|error|unexpected-response` or `target.close|error|unexpected-response`. A normal upstream `message` event does NOT trigger close — it triggers the line-131 handler which just forwards via `source.send()`. Verified by re-reading the full `proxyWebSockets` function body — no spurious close paths.

### H6 — k6 client's WS `message` event doesn't fire on text vs binary mismatch

**Status:** WEAK / probably-not-relevant.

mock-litellm sends `socket.send(JSON.stringify(event))` (`compose/mock-litellm/src/realtime.ts:30`). The `ws` library treats a `string` argument as a TEXT frame (RFC 6455 opcode 0x1). The proxy at line 131 receives `(data, binary)` where `binary=false` and `data` is a `Buffer` (the `ws` library always wraps inbound payloads as Buffer in its 'message' event — that's a known v8 behavior, see `ws` README "Receiving data"). It then calls `source.send(buffer, { binary: false })` — `ws` honours the explicit `binary:false` and emits a TEXT frame. k6's `k6/websockets` `addEventListener('message', cb)` fires on both text and binary frames (the underlying `nhooyr/websocket`-style Go client surfaces both). So even if the proxy got the frame, k6 would see it.

This hypothesis remains WEAK rather than REJECTED only because we cannot reproduce — once the root cause is fixed and frames flow, we should verify the k6 client actually decodes the JSON correctly.

### H7 [NEW] — k6 adapter uses the wrong WebSocket constructor signature

**Status:** STRONG / probable root cause.

#### Evidence

1. `tools/load-test/src/utils/http-client.ts:144-156` (`k6Ws` function):
   ```ts
   const W = (ws as { WebSocket: new (u: string, p: WsParams) => WsSocket }).WebSocket;
   const socket = new W(url, params);  // ← 2 ARGS
   ```
2. `k6/websockets` ([Grafana docs](https://grafana.com/docs/k6/latest/javascript-api/k6-experimental/websockets/)) requires:
   ```js
   new WebSocket(url, protocols, params)  // ← 3 ARGS
   ```
   where `params` is the object carrying `headers` and `tags`.
3. With the 2-arg form, k6 binds our `{ headers: { authorization: 'Bearer …' }, tags: { endpoint: 'realtime-ws' } }` to the `protocols` slot. k6's goja layer probably stringifies the object (or rejects it as a non-array) — either way the `headers` field never reaches the WS handshake.
4. **API dualAuthHook** (`apps/api/src/middleware/dual-auth.ts:123`) runs as `onRequest` on EVERY route including `/v1/realtime` (no `auth:false` opt-out on the proxy route — `apps/api/src/routes/realtime.ts:124-172`). With no `authorization` header, `auth.api.getSession()` returns `null`, `tryPreviousToken` also fails, `AuthError("unauthorized")` is thrown, the centralized error handler emits a 401 envelope, and the WS upgrade is aborted BEFORE @fastify/http-proxy's handler runs.
5. **Run 4 metrics support this exactly:**
   - `ws_sessions: 168 836` — incremented per `client.ws()` callback regardless of upgrade success.
   - `ws_connecting p95: 5.5ms` — TCP+TLS+upgrade time, includes the 401-response path (still fast).
   - **No `ws_msgs_sent` line in the run log** — `socket.send(PING_PAYLOAD)` in the `open` listener never fires because `open` never fires (the upgrade failed).
   - **No `ws_msgs_received` line** — same root cause.
   - `realtime_ws_roundtrip_ms` Trend empty — recorded only inside the `message` listener which never runs.

#### Why this is invisible in tests

- **Vitest unit tests** for the realtime-ws flow (`tools/load-test/src/flows/realtime-ws.ts` consumers) inject a `MockAdapter` whose `ws()` synchronously calls `handler(socket)` with a stub socket and dispatches `open` + `message` events manually. The constructor signature is never exercised.
- **`apps/api/src/routes/realtime.test.ts`** uses Node's standard `ws` library (`new WebSocket(wsUrl, { headers: {…} })`) which DOES accept headers in the 2-arg form. This test passes — masking the k6-specific bug.
- **smoke.ts** also uses `new WebSocket(url, params)` indirectly (it imports `WebSocket` directly from `k6/websockets` at line 28 but follows the same 2-arg pattern as the adapter — verify this in the fix).

#### Sub-claim: smoke.ts may have the same bug

`tools/load-test/src/smoke.ts:28` imports `WebSocket` from `k6/websockets`. If smoke.ts also constructs the WS with 2 args, the fix must land in BOTH places (adapter + smoke). Verify during planning.

## Recommended fix

### Primary fix — k6 adapter constructor signature

**File:** `tools/load-test/src/utils/http-client.ts`

**Lines 144-156** — change `k6Ws`:

```ts
function k6Ws(url: string, params: WsParams, handler: (socket: WsSocket) => void): WsResponse {
  const ws = (globalThis as unknown as { __k6_ws?: unknown }).__k6_ws;
  if (!ws) {
    throw new Error("createK6Adapter().ws invoked outside the k6 runtime");
  }
  // k6/websockets exports WebSocket; the constructor takes
  // (url, protocols, params). Phase 08.4 fix — previously called as
  // (url, params) which silently dropped `headers` + `tags`.
  const W = (ws as {
    WebSocket: new (u: string, p: string[] | null, opts: WsParams) => WsSocket;
  }).WebSocket;
  const socket = new W(url, null, params);
  handler(socket);
  return { status: 101 };
}
```

Type-level change: bump the `WebSocket` constructor type to a 3-arg signature with `protocols: string[] | null`.

### Secondary fix — smoke.ts (if it has the same bug)

**File:** `tools/load-test/src/smoke.ts`

Locate every direct `new WebSocket(url, …)` call. Ensure each follows the 3-arg form. Add a comment cross-referencing the adapter fix so the bug doesn't regress.

### Defensive — add a coverage check that fails on 2-arg WS construction

Add a vitest assertion that the k6 adapter's `ws()` implementation, when invoked under a stubbed `__k6_ws`, calls the constructor with 3 arguments and `null` in slot 2. This is a future-regression guard (Stage B back-fill discipline). Suggested test file: `tools/load-test/src/utils/http-client.test.ts` (extend existing if present, else new).

### Rationale

- **Smallest blast radius**: fixes the bug at its source without touching api code, the proxy config, or the upstream mock — all of which are already correct.
- **Empirically grounded**: every claim above is anchored to a file + line number; no speculation.
- **Test-first compatible**: a RED test that mounts a real `ws.WebSocketServer` upstream and asserts the `authorization` header arrives produces zero false GREEN — the fix flips the assertion from "header missing" to "header present."
- **No risk to security posture**: the master-key swap, SSRF gate, host-header preservation, 10s handshakeTimeout, and preHandler order are all untouched. The proxy code path is identical pre- and post-fix.

## Alternative fallback

If — and only if — after landing the adapter fix the smoke test reveals the `@fastify/http-proxy` v11 path is genuinely broken for upstream→client frame forwarding, the fallback is to **replace the proxy plugin with a hand-rolled Fastify+ws bridge**:

```ts
// Sketch ONLY — do NOT implement until adapter fix is verified insufficient.
app.get('/v1/realtime', { websocket: true, preHandler: authPreHandler }, (clientSocket, req) => {
  const upstreamUrl = new URL('/v1/realtime', upstreamWs);
  upstreamUrl.searchParams.set('user', req.user.id);
  const upstream = new WebSocket(upstreamUrl, {
    headers: buildRewriteRequestHeaders(masterKey)(req.headers, req),
    handshakeTimeout: 10000,
  });
  upstream.once('open', () => {
    clientSocket.on('message', (data, binary) => upstream.send(data, { binary }));
    upstream.on('message', (data, binary) => clientSocket.send(data, { binary }));
  });
  clientSocket.on('close', () => upstream.close());
  upstream.on('close', () => clientSocket.close());
  // error + ping/pong wiring elided for brevity
});
```

**Code cost:** ~60 lines of Fastify+ws wiring + ~120 lines of test (handshake, frame forward, close cascade, auth fail).
**Lose:** automatic reply.from() HTTP fallback that http-proxy gives on GET-without-upgrade. (We don't rely on this — diagnostic probes go through `/healthz`.)
**Gain:** complete control over the upgrade lifecycle. Easier to debug.

**Decision rule:** only switch to the fallback if the post-fix run log shows `ws_msgs_sent>0`, `ws_msgs_received=0`, AND `realtime_ws_roundtrip_ms` is still empty. That combination is the unambiguous signature of "client sends, server receives client frame, upstream sends, proxy drops upstream frame." Anything else means the adapter fix is sufficient.

## Pitfalls and risks

1. **`auth: false` opt-out temptation.** Do NOT mark the realtime route with `config.auth: false` to "bypass" the auth check during debugging. The route is security-sensitive (T-03-07-01: master-key leak). The k6 client must carry a real bearer; if it doesn't, the FIX is on the client, not the route.

2. **`req.raw.url` mutation ordering.** The preHandler at `realtime.ts:167-170` writes `req.raw.url = u.pathname + u.search` AFTER reading `req.raw.url ?? req.url`. Any future refactor that hoists this above the auth check breaks the `T-03-07-04` (?user= overwrite) test. Lock this ordering with an assertion-comment in the source.

3. **Host header rewriting.** `@fastify/http-proxy` v11 forwards `host: <upstream-host>` by default (via `@fastify/reply-from`). The current `rewriteRequestHeaders` does NOT touch `host`. If we ever introduce per-request `host` rewriting (e.g., to satisfy LiteLLM's virtual-key routing), it must land in `rewriteRequestHeaders` and we must add a test that asserts the upstream sees the correct `host:` for both wsUpstream and HTTP-side requests.

4. **`handshakeTimeout: 10000`.** Phase 04 / D-27 locked this at 10s. The fix must NOT alter it — handshakeTimeout governs the TCP+upgrade ceiling on the api→upstream side (independent of the client→api timeout, which is controlled by the entrypoint config in Traefik). A 30-second mock-litellm cold start under load is plausible enough that anything shorter risks false failures.

5. **SSRF gate.** `apps/api/src/lib/outbound-fetch.ts` and the `OUTBOUND_PRIVATE_HOST_ALLOWLIST` allow-list `litellm` as a private host. The proxy's `ws://litellm:4000` upstream is reached via the `ws` library which uses its own internal `net`+`tls` connection — NOT the wrapped undici dispatcher. The SSRF gate does NOT intercept `ws://` upgrades. This is by design (the gate is for outbound HTTP calls from user-facing code), and the realtime proxy is operator-configured so the upstream is trusted. No action needed; flag for the planner if a future operator wants per-request SSRF on WS.

6. **k6 protocols argument.** `null` is the documented value for "no subprotocols." If a future Realtime API revision requires a specific subprotocol (e.g., `'openai-realtime'`), update both the k6 adapter (`new W(url, ['openai-realtime'], params)`) and the api proxy (the `ws` library forwards `source.protocol` to the upstream as the requested subprotocol, line 470-472 of http-proxy index.js).

7. **`ws_sessions` is a misleading metric.** It counts every `client.ws()` invocation, not successful upgrades. Do NOT use it as a proxy for "WS health." After the fix lands, the canonical health signal is `ws_msgs_sent > 0 AND ws_msgs_received > 0 AND realtime_ws_roundtrip_ms.count > 0`.

8. **Re-running the 30-min plateau costs real operator time.** Before re-running, do a 1-VU 10-second smoke (`make load-test PROFILE=mock VUS=1 DURATION=10s` if the Makefile target supports it; else a direct k6 invocation) to confirm the adapter fix lands and the metric populates. Only then run the full plateau.

## State of the art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
