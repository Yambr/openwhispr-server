# Phase 08.4 Umbrella: realtime-ws proxy forwarding fix

## Scope pivot (CRITICAL — read before executing)

The ROADMAP.md Phase 08.4 entry frames the bug as api-side `@fastify/http-proxy` v11 frame forwarding. **Research file `08.4-RESEARCH.md` REJECTED that hypothesis** with direct source review of `@fastify/http-proxy@11.4.4/index.js` lines 94-160 (`proxyWebSockets`) — bidirectional `source.on('message') → target.send()` and `target.on('message') → source.send()` are both wired and intact.

**Actual root cause (H7 — HIGH confidence):** The k6 load-test adapter at `tools/load-test/src/utils/http-client.ts:152-153` constructs `new W(url, params)` with TWO arguments. The `k6/websockets` module signature is `new WebSocket(url, protocols, params)` with THREE arguments. With the 2-arg form, our `params` object (`{ headers: { authorization: 'Bearer …' }, tags: { endpoint: 'realtime-ws' } }`) is bound to the `protocols` slot and silently discarded. The WS upgrade goes out with NO `Authorization` header, the api's `dualAuthHook` throws `AuthError('unauthorized')` BEFORE the proxy upgrade fires, k6 records a 101-counted `ws_session` but the `open` event never fires, `socket.send()` never runs, no upstream echo arrives, no `realtime_ws_roundtrip_ms` data point is recorded.

This is a **k6-client-adapter bug**, NOT an api-side proxy bug. The Run 4 metrics back this up cleanly: `ws_sessions=168 836`, `ws_connecting p95=5.5ms`, but `ws_msgs_sent` and `ws_msgs_received` lines are entirely absent from the k6 summary — the unambiguous signature of "upgrade failed at auth, `open` never fired."

Verified during planning: `tools/load-test/src/smoke.ts:79` and `tools/load-test/src/main.ts:89` already use the correct 3-arg `new WebSocket(url, undefined, params)` form. Only `http-client.ts:152-153` has the typo. The fix is therefore scoped to a single 1-line constructor signature change plus a regression test plus a smoke-gate assertion.

## Threat model

This fix has **zero new attack surface**. It RESTORES the auth flow that was silently bypassed by a typo on the client side. No api code changes; the master-key swap, SSRF gate, host-header preservation, `handshakeTimeout: 10000`, preHandler ordering, and dualAuthHook are all untouched. The threat register inherited from Phase 03/04/07 remains in force; no new STRIDE entries required.
