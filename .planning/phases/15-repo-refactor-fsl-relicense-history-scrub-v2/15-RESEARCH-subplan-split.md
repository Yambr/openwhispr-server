**Rationale:** Recommend **Option B (4 plans)** for this project. The defining constraint is PITFALLS §10: the history scrub is an irreversible operational event (lock branch protection → force-push → unlock → CI cache invalidation → re-lock) that must own its execution window and cannot share a plan with anything landing afterward. Bundling the FSL codemod with the scrub (Options A, D) conflates a reviewable code change (675 SPDX headers via `reuse` — normal PR, normal CI gates, normal rollback via revert) with a non-revertible process event (filter-repo + force-push — no `git revert` recovery). Separating them (B's 15-03 vs 15-04) lets the codemod go through standard ≥90/90/90/90 verification and merge-queue, then 15-04 becomes a pure runbook execution with a small diff (just the filter-repo invocation log + runbook doc). Option C over-fragments — STRUCT-02..07 all touch overlapping infra files (`docker-compose.yml`, Traefik config, `apps/web/public/`) so forcing them into separate PRs creates conflict storms without atomicity gain. Option B's 15-01 (test-layout MOVE-INVENTORY) is also a useful cheap pre-flight that surfaces path collisions before the bulk 15-02 reorg, matching the constitutional TDD discipline (tests-first ordering applies at the plan level too: codify the test layout convention, then execute moves against it). The 15-02 → 15-03 ordering must be enforced (codemod runs against final paths, not pre-move paths) but this is a merge-queue concern, not a plan-design concern. Net effect: 4 atomic commits aligned with 4 distinct risk profiles (convention, structural moves, mechanical relicense, irreversible history event), matching GSD wave semantics where 15-04 is necessarily a solo terminal wave.
