## Test-Layout Migration Strategy (STRUCT-01)

| Option | Pros | Cons | Complexity | Recommendation |
|--------|------|------|------------|----------------|
| **A. Big-bang `git mv` codemod** | Single semantic event; clean repo after merge; matches `Phase15-MOVE-INVENTORY.md` deliverable (one inventory = one move); satisfies STRUCT-01 "convention codified" unambiguously; vitest.config `include` patterns updated once | Massive diff (~100+ files); blocks/conflicts with every in-flight branch for the merge window; collides head-on with FSL codemod (15.b) which also touches every file; reviewer cognitive load extreme | ~100+ files moved, 1 codemod tool added, 5-8 `vitest.config.ts` `include` patches, all relative-import paths in test files rewritten via ts-morph — Risk: import-rewrite bugs slip past type-check if dynamic imports used; merge-window must be coordinated with 15.b | Rec if 15.b lands in same atomic PR (combine into one "structural reflow" PR) OR if no other phase-15 work is in flight |
| **B. Phased per-app/package** | Smaller PRs (4 total); easier review; partial rollback; each PR fully green | Intermediate states are inconsistent (CLAUDE.md/conventions docs lag behind reality); STRUCT-01 not "codified" until PR4 merges; FSL codemod collision spread across 4 windows instead of 1; `vitest.config.ts` `include` patterns churn 4 times | 4 PRs, each ~20-40 files; ts-morph import-rewrite re-runs per PR; ESLint no-colocated-tests rule lands in PR4 only — Risk: PR2/PR3 reviewers see inconsistent layout, may push back; convention drift between PRs | Rec if FSL codemod (15.b) is already in flight or if review bandwidth is the binding constraint |
| **C. Strangler (new tests only)** | Zero churn; zero migration risk; zero FSL collision | Codebase stays mixed forever; STRUCT-01 success criterion "convention codified" technically met (doc exists) but layout itself not migrated → fails the *intent*; `Phase15-MOVE-INVENTORY.md` deliverable becomes empty/vestigial; ongoing reviewer friction every PR ("which layout does this go in?") | 1 doc file + 1 ESLint warn rule; zero file moves — Risk: convention rots; future contributors copy nearest neighbor and mixed layout entrenches | Not recommended — fails Phase15-MOVE-INVENTORY deliverable intent |
| **D. Hybrid (apps split, packages co-located)** | Respects library vs app idiom (packages = library convention, apps = product convention); aligns with Turborepo/Next.js monorepo precedent (apps tend to externalize tests, packages keep co-located); smaller move than A | Requires explicit two-rule explanation in `docs/conventions.md`; arguably violates "uniform convention"; ESLint rule must be path-scoped (allow co-located under `packages/*/src`, forbid under `apps/*/src`); `Phase15-MOVE-INVENTORY.md` is shorter but split-brain | ~40-60 files moved (apps only); 2-3 `vitest.config.ts` patches; ESLint rule with path overrides; conventions doc with 2 worked examples — Risk: future contributors miss the apps/packages distinction; ESLint must enforce mechanically | Rec if reviewer pushback on "library convention" is anticipated OR if package tests use heavy fixtures co-located with source |

**Rationale:** For a strict-TDD, ≥90/90/90/90-on-diff, enterprise-grade codebase where `Phase15-MOVE-INVENTORY.md` is a named deliverable mandating an explicit pre-move inventory, **Option A (big-bang) is the principled pick *if and only if* it is co-landed with the FSL codemod (15.b)** in a single "structural reflow" PR — the two codemods touch the same files (FSL renames symbols, test-move relocates files), and serializing them doubles the merge-window pain while only marginally reducing review load. The single-PR coordination matches the inventory-first deliverable shape (one inventory, one move, one green CI run). If 15.b cannot be co-landed, fall back to **Option B**: land STRUCT-01 first as 4 small PRs (api → web → packages → conventions+ESLint), accepting transient inconsistency, because the project's TDD discipline already requires every PR to be green and B's per-PR atomicity preserves that invariant. Option C fails the spirit of STRUCT-01 ("layout itself not migrated") and renders `Phase15-MOVE-INVENTORY.md` vestigial. Option D's library-vs-app split has real industry precedent (Turborepo, Next.js monorepo) but introduces a permanent two-rule cognitive tax that contradicts the project's "boring, uniform" stack ethos; only choose D if package-level co-located fixtures (e.g., `packages/wire-schemas/src/__tests__/fixtures/*.json`) are heavy enough that moving them costs real semantic effort. On `vitest.config.ts`: in all options, switch `include` from default `**/*.{test,spec}.ts` to explicit `tests/**/*.test.ts` patterns post-move, and consider Vitest 3.2+ `projects` config (replaces deprecated `workspace`) to scope unit vs integration vs e2e per directory — this is a one-time win regardless of A/B/D choice. Reviewer cognitive load favors A (one shock) over B (four smaller shocks) only if the reviewer has uninterrupted time to read 100+ file moves; in practice B wins on async-review monorepos. **Final pick: Option A co-landed with 15.b in one PR; fallback to Option B if 15.b timing diverges.**
