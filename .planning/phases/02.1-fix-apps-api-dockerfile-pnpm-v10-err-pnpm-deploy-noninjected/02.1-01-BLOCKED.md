# Plan 02.1-01 — BLOCKED: deeper Phase 02 architectural defect uncovered

## Status

Plan 02.1-01 attempted both candidate fixes from CONTEXT.md (variant A: `inject-workspace-packages`, variant B: multi-stage Dockerfile rewrite without `pnpm deploy`). **Neither closes the issue cleanly** because both expose a separate, pre-existing architectural defect in Phase 02's build setup that must be addressed first.

No changes to source/Dockerfile/workspace config landed. The investigation findings are captured here so the next attempt can start from solid ground.

## What was tried

### Variant A — `inject-workspace-packages: true`

**Result: NOT HONORED by pnpm 11.0.8.**

- Added `inject-workspace-packages: true` to `pnpm-workspace.yaml` → `pnpm config get inject-workspace-packages` returns `undefined`
- Added `inject-workspace-packages=true` to root `.npmrc` → also `undefined`
- `pnpm install --force` and `pnpm install` after `rm -rf node_modules` both produced symlinked workspace deps (e.g., `apps/api/node_modules/@openwhispr/data` is a symlink to `../../../../packages/data`)
- `pnpm --filter @openwhispr/api --prod deploy /out` continued to throw `ERR_PNPM_DEPLOY_NONINJECTED_WORKSPACE`

This may indicate a documentation/version gap in pnpm 11.0.8, OR the flag may require companion `dependenciesMeta.{name}.injected: true` annotations in each consumer's `package.json`. Either way, NOT a one-line fix as CONTEXT.md D-02 had hoped.

### Variant B — multi-stage Dockerfile without `pnpm deploy`

**Result: BLOCKED by Phase 02 build-architecture defect.**

While drafting the variant-B Dockerfile (using `pnpm install --prod --node-linker=hoisted` for a flat runtime `node_modules` + explicit `COPY --from=builder` of built workspace artifacts), discovered that **the workspace packages api consumes are not bundled at all**:

| Symptom | Evidence |
|---------|----------|
| `apps/api/dist/index.js` keeps `import "@openwhispr/data/schema"` and `import "@openwhispr/contract-tests/schemas"` external | `grep -n "@openwhispr/" apps/api/dist/index.js` shows 8+ unbundled imports |
| `packages/data/package.json` `exports` map points `./schema → ./src/schema/index.ts` (TypeScript source, not built JS) | manifest is unmodified |
| `packages/data/tsup.config.ts` only builds `migrate.js` (the standalone migrate-service entry), NOT a library bundle for api consumption | comment in file: "the one-shot migrate compose service runs node /app/packages/data/dist/migrate.js" |
| `packages/contract-tests/package.json` `build` script is `tsc -p tsconfig.json --noEmit` — emits NOTHING | `cat packages/contract-tests/package.json` |

**Implication:** Even before pnpm v10, `pnpm deploy` only worked because it copied `packages/{data,contract-tests}/src/` into `/out/node_modules/@openwhispr/{data,contract-tests}/src/`, AND something must have transpiled those `.ts` files at runtime for Node 24 to load them. Either:
- (a) Node 24 was loading `.ts` directly via experimental loader (unlikely, would require `--experimental-strip-types` or `--experimental-loader=tsx/esm`)
- (b) The container shipped tsx/ts-node and the entrypoint or CMD invoked it (current entrypoint shows plain `node /app/dist/index.js`)
- (c) The api container was never actually starting cleanly even before pnpm v10 — and nobody noticed because compose-up failed at the MinIO pin step earlier in the chain

Option (c) is most likely. **The "before pnpm v10" Dockerfile was not actually a working artifact end-to-end** — it's a compose-up earliest-failure-wins artifact.

## Root architectural problem

Phase 02 ships api with workspace dependencies whose build outputs do not match what api's runtime imports require. Three packages are affected:

| Package | `main` / `exports` target | tsup output | api imports | Gap |
|---------|--------------------------|-------------|-------------|-----|
| `@openwhispr/data` | `src/index.ts`, `./schema → src/schema/index.ts`, `./client → src/client.ts` | only `dist/migrate.js` (CJS, for migrate-service) | `from "@openwhispr/data"`, `from "@openwhispr/data/schema"` | No library bundle; runtime needs the `.ts` source AND a way to load it |
| `@openwhispr/contract-tests` | `src/index.ts`, `./schemas → src/schemas.ts` | NONE (`build` is `tsc --noEmit`) | `from "@openwhispr/contract-tests/schemas"` | No bundle at all; runtime needs the `.ts` source |
| `@openwhispr/api` | `src/index.ts` | `dist/index.js` (ESM bundle) + `dist/scripts/check-default-secrets.cjs` | (consumed by container CMD) | api itself bundles fine; the externals don't |

## Required fix scope (NOT this phase)

This is no longer a Dockerfile-tweak; it's a Phase 02 build-architecture correction. Three viable directions:

| Option | Change | Where | Effort |
|--------|--------|-------|--------|
| **B1. Inline workspace deps into api bundle** | Add `noExternal: [/^@openwhispr\//]` to `apps/api/tsup.config.ts` so the api bundle becomes self-contained | 1 line in tsup config; rebuild api; runtime image just needs `node_modules` for non-workspace deps | Smallest |
| **B2. Build proper library bundles for `data` and `contract-tests`** | Add a `library` tsup entry in each, output ESM/CJS, update `exports` maps to point at `./dist/` | New tsup configs in 2 packages, manifest changes, Dockerfile copies dist instead of src | Medium — proper architecture, also fixes consumption from outside Docker |
| **B3. Ship tsx in the runtime image and run via tsx** | Container entrypoint becomes `tsx /app/dist/index.js` (or copy api `src/` and run `tsx src/index.ts`) | Runtime image bloat; defeats the purpose of building a JS bundle | Worst |

**Recommendation: B1** — add `noExternal: [/^@openwhispr\//]` to api's tsup config. The api bundle becomes self-contained, the runtime image only needs `pnpm install --prod` of non-workspace deps, and a clean multi-stage Dockerfile becomes trivially correct.
