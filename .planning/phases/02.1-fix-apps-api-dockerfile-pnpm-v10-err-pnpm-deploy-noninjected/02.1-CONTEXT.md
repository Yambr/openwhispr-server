# Phase 02.1 — CONTEXT

## Phase Goal

Fix `apps/api/Dockerfile` so the `migrate` and `api` images build cleanly under pnpm v10/v11. Unblock Phase 01.1 Plan 05 (`docker compose --profile default up --wait`).

## Background

Phase 01.1 Plan 05 (Wave 3) tried to prove the full stack boots clean as exit-gate verification of the MinIO image-pin fix. It reached `docker compose pull` ✓ but `docker compose up --wait` exited 17 with:

```
#17 [migrate builder 13/14] RUN pnpm --filter @openwhispr/api --prod deploy /out
[ERR_PNPM_DEPLOY_NONINJECTED_WORKSPACE]
By default, starting from pnpm v10, we only deploy from workspaces
that have "inject-workspace-packages=true" set
```

This defect was always present; it was hidden behind the now-fixed MinIO pull failure.

## Locked Decisions

### D-01 — NO `--legacy` workaround
Per project enterprise rule (`feedback_no_workarounds_enterprise.md`), do NOT add `--legacy` to `pnpm deploy`, do NOT set `force-legacy-deploy=true` in `.npmrc`. These are escape hatches that hide a real architectural change pnpm v10 made deliberately.

### D-02 — Approach: multi-stage Dockerfile WITHOUT `pnpm deploy` (variant B)

**Variant A (`inject-workspace-packages: true`) was attempted and FAILED on pnpm v11.0.8.**

Empirical findings (2026-05-09 in this phase):
- Adding `inject-workspace-packages: true` to `pnpm-workspace.yaml` had no effect — `pnpm config get inject-workspace-packages` returns `undefined`
- Adding `inject-workspace-packages=true` to a root `.npmrc` likewise had no effect
- `pnpm install --force` after either change still produced symlinked workspace deps (e.g., `apps/api/node_modules/@openwhispr/data` is a symlink to `../../../../packages/data`)
- `pnpm --filter @openwhispr/api --prod deploy /out` continues to throw `ERR_PNPM_DEPLOY_NONINJECTED_WORKSPACE`

This may reflect a documentation/behavior gap in pnpm 11.0.8, or the flag may require additional `dependenciesMeta.{name}.injected: true` annotations in each consumer's `package.json` (which would be invasive in its own right). Either way, it's not a clean one-line fix.

**Variant B is the chosen fix:** Rewrite `apps/api/Dockerfile` to NOT use `pnpm deploy` at all. Use a standard multi-stage layout:

1. **deps stage** — `pnpm install --frozen-lockfile --prod --filter @openwhispr/api...` to install only runtime deps (excluding devDeps)
2. **builder stage** — full install (with dev), build `@openwhispr/data` then `@openwhispr/api` via tsup
3. **runtime stage** — `node:24-alpine` minimal image; `COPY --from=deps` the pruned `node_modules`, `COPY --from=builder` the built `dist/` outputs of api + data; restore the existing entrypoint, healthcheck, USER node, secrets check

Why this is the proper enterprise fix:
- Industry-standard multi-stage pattern; doesn't depend on any `pnpm deploy` quirk
- Reproducible — relies only on `pnpm install --prod` semantics that have been stable for years
- Smaller runtime image (excludes pnpm itself, devDeps, source files)
- Forward-compatible with any future pnpm major version
- Explicit control over what lands in the runtime image (auditable)

**Workspace symlink handling in runtime:** Because `pnpm install` symlinks `@openwhispr/data` from `apps/api/node_modules/@openwhispr/data → ../../../../packages/data`, the runtime stage MUST copy `apps/api/node_modules` (with the symlink) AND copy `packages/data/dist` to the symlink target path. This recreates the resolution chain Node will follow at runtime.

### D-03 — Validation matrix
Validate all of the following BEFORE closing the phase:
- [ ] `pnpm install --frozen-lockfile` succeeds at repo root
- [ ] `pnpm typecheck` passes (no workspace resolution regressions)
- [ ] `pnpm test` passes (unit tests across all workspace packages)
- [ ] `docker buildx build -f apps/api/Dockerfile .` builds successfully (image builds clean — both `migrate` target and `api` target)
- [ ] `docker compose --profile default up --wait --wait-timeout 240` exits 0 (full stack boots, all services pass healthcheck)

Test order matters: cheap → expensive. Stop at first failure with full diagnostic.

### D-04 — Lockfile regen scope
`inject-workspace-packages: true` MAY require lockfile regeneration. If `pnpm install --frozen-lockfile` fails after the config change, run `pnpm install --no-frozen-lockfile` once to regenerate, then commit the lockfile delta. Do NOT auto-update non-workspace deps in the same change.
