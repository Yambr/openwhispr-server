# Internationalization (i18n) — Operator Guide

> Phase 10 / Plan 10-03 (DOCS-04). Operator-facing reference for the
> OpenWhispr Server i18n surface. Companion documents:
> [`architecture.md`](./architecture.md) §5,
> [`operations.md`](./operations.md) (i18n volume runbook),
> [`security.md`](./security.md) (audit-log English-only guard).

OpenWhispr Server ships with English (`en`) as the source locale and
Russian (`ru`) as the second runtime locale. Both are fully wired
through the api error envelope, the worker email templates, and the
web UI bundle. Operators can mount additional locale bundles at
runtime via `LOCALES_DIR` without rebuilding the images.

This document covers:

1. Supported locales today and the roadmap.
2. The locale negotiation chain (api and web).
3. The resource file layout (server vs web; why two homes).
4. A step-by-step recipe to add a new locale.
5. The operator-override mechanism (`LOCALES_DIR`).
6. CLDR plural categories — quick reference for translators.
7. The English-only source-artifact rule and where the exemptions live.
8. Email template locale selection.
9. Troubleshooting.

---

## 1. Supported locales

| Locale | Status | Bundles                                                          | Plural categories            |
| ------ | ------ | ---------------------------------------------------------------- | ---------------------------- |
| `en`   | source | api error codes, worker email templates, web UI                  | `one`, `other`               |
| `ru`   | runtime | api error codes, worker email templates, web UI                 | `one`, `few`, `many`, `other`|

Roadmap (out of scope for v1, tracked for v1.x):

- `es`, `fr`, `de` — Latin-1 scripts, mechanically straightforward;
  blocked only on translator availability.
- CJK locales (`zh`, `ja`, `ko`) — deferred to v2; require width-aware
  layout work in the web UI.
- RTL locales (`ar`, `he`) — deferred to v2; require directional CSS
  audit across the web UI components.

The constitutional bar to add a new locale is full parity with `en`
across every namespace (`errors`, `auth`, `email`, `web`). CI gates
this with the `i18n-completeness` job (see §4 below).

## 2. Locale negotiation chain

### 2.1 api (server)

`apps/api/src/i18n/init.ts` mounts the `i18nPlugin` on the Fastify
instance. The plugin is `i18next` + `i18next-icu` +
`i18next-fs-backend` + `i18next-http-middleware`. Per-request the
negotiation chain is:

1. **`Accept-Language` header** — parsed by
   `i18next-http-middleware`; the first locale on `supportedLngs`
   wins.
2. **Per-user `users.locale`** — when the request is authenticated
   and the resolved user has a non-null `locale`, the user's locale
   overrides the header (Phase 10 Plan 10-01c).
3. **Fallback** — `en`.

`req.i18n.t("errors.<code>")` resolves against the chosen locale.
Routes never format strings; they throw typed errors with a stable
`code` literal that the centralized `setErrorHandler` translates.

### 2.2 web (Next.js 15 App Router)

`apps/web/src/middleware.ts` is the Edge-runtime locale negotiator.
The chain is:

1. **`NEXT_LOCALE` cookie** — preferred when set by the user via the
   language switcher.
2. **`Accept-Language` header** — fallback when the cookie is unset.
3. **Fallback** — `en`.

The negotiated locale is forwarded to RSC layouts via an `x-locale`
request header. `apps/web/src/lib/i18n.ts` reads the header on the
server-component side; the client-component side reads the cookie
through the `LanguageSwitcher` component. `POST /api/locale` is the
write endpoint that sets the cookie (Plan 10-02).

## 3. Resource file layout

i18n bundles live in two homes by design:

| Home                                | Loaded by             | Hot-reload | Notes                                                |
| ----------------------------------- | --------------------- | ---------- | ---------------------------------------------------- |
| `apps/api/src/i18n/locales/<lng>/`  | `i18next-fs-backend`  | runtime    | api request envelope; ICU MessageFormat              |
| `apps/worker/src/i18n/locales/<lng>/email/<template>/` | `WorkerTemplateRenderer` | runtime | email subject + body.txt + body.html               |
| `apps/web/src/locales/<lng>/`       | Next.js bundler       | build      | static-imported into the web bundle                  |

Why two homes:

- **Server bundles are runtime files.** The api and worker open them
  at startup with `i18next-fs-backend`, so an operator can mount a
  replacement directory via `LOCALES_DIR` (§5) and override the
  bundled translations without a rebuild.
- **Web bundles are build-time.** Next.js 15 App Router static-imports
  the JSON to keep the Edge-runtime cold-start small. Replacing a web
  bundle requires a rebuild of the `web` container image. The
  language-switcher cookie at runtime selects which pre-built bundle
  renders; it does not load alternative bundle content.

Both homes share the same JSON structure for `errors`:

```json
{
  "errors": {
    "validation_failed": "Validation failed",
    "unauthorized": "Unauthorized",
    "rate_limit_exceeded": "Rate limit exceeded"
  }
}
```

ICU MessageFormat is enabled for pluralization on both homes
(`i18next-icu` server-side, `intl-messageformat` web-side).

## 4. How to add a new locale (recipe)

The example below adds Spanish (`es`) to a fresh checkout. Replace
`es` with your locale tag throughout.

```bash
# 1. Create the directory layouts.
mkdir -p apps/api/src/i18n/locales/es
mkdir -p apps/worker/src/i18n/locales/es/email/{email_verification,password_reset,account_deletion_confirmation}
mkdir -p apps/web/src/locales/es

# 2. Copy the en bundle as a starting point.
cp apps/api/src/i18n/locales/en/errors.json apps/api/src/i18n/locales/es/errors.json
cp -r apps/worker/src/i18n/locales/en/email/* apps/worker/src/i18n/locales/es/email/
cp -r apps/web/src/locales/en/* apps/web/src/locales/es/

# 3. Translate every leaf value (NOT the keys).

# 4. Register the locale.
#    apps/api/src/i18n/init.ts -> supportedLngs: ["en", "ru", "es"]
#    apps/web/src/lib/i18n.ts  -> supportedLocales: ["en", "ru", "es"]

# 5. Add to the i18n-completeness CI gate inventory.
#    tests/i18n/completeness.test.ts (or the test that lists supported locales)

# 6. Run the completeness gate locally.
pnpm test:i18n-completeness
```

The `i18n-completeness` CI job (`.github/workflows/ci.yml`) fails the
PR if any error code defined in `en` is missing from the new locale,
or any per-instance code emitted by `new <TypedError>(code, message)`
in the route tree is not translated. The `ts-morph`-based scanner
catches both class-default codes and per-instance overrides.

## 5. Operator-override mechanism: `LOCALES_DIR` (I18N-02)

Both api and worker honour `process.env.LOCALES_DIR` before falling
back to the bundled `dist/i18n/locales`. This lets an operator drop a
corrected or extended translation set into a running deployment
without rebuilding the container image.

### 5.1 docker-compose

`docker-compose.yml` already binds `./locales:/app/locales:ro` on the
api and worker services and sets `LOCALES_DIR=/app/locales`:

```yaml
api:
  environment:
    LOCALES_DIR: /app/locales
  volumes:
    - ./locales:/app/locales:ro
worker:
  environment:
    LOCALES_DIR: /app/locales
  volumes:
    - ./locales:/app/locales:ro
```

To activate an override:

1. Create `./locales/en/errors.json` (and any other namespace files
   you want to override). Files NOT in the override dir fall back to
   the bundled `dist/i18n/locales`.
2. Restart api + worker:

   ```bash
   docker compose restart api worker
   ```

3. Inspect the structured boot log: api emits
   `event=i18n.locales_dir, dir=/app/locales, locales=[en,ru,...]`.

### 5.2 Kubernetes (Helm)

The Helm chart at `charts/openwhispr/` accepts a ConfigMap of locale
overrides:

```yaml
# values.yaml
i18n:
  overrides:
    enabled: true
    configMapName: openwhispr-locales-override
```

Create the ConfigMap from a directory tree:

```bash
kubectl create configmap openwhispr-locales-override \
  --from-file=locales/ \
  -n openwhispr
```

The chart mounts it at `/app/locales` and sets `LOCALES_DIR` on api
and worker pods. The api pod's readiness probe explicitly hits a
warmed `errors.<code>` lookup so a broken override JSON fails the
rolling deploy instead of serving 500s.

### 5.3 Validation at boot

Both api and worker validate the resolved `LOCALES_DIR` at startup:

- the directory must exist and be readable (otherwise the process
  exits with a fatal log and a clear remediation hint);
- the bundled fallback dir is always loaded too, so a sparse override
  directory is fine (any missing key falls back to bundled, ultimately
  to `en`).

## 6. CLDR plural quick reference

Russian uses four CLDR plural categories: `one`, `few`, `many`,
`other`. The boundaries are:

| Category | Rule (CLDR)                                                  | Example numbers                |
| -------- | ------------------------------------------------------------ | ------------------------------ |
| `one`    | `n % 10 == 1 and n % 100 != 11`                              | 1, 21, 31, 41, 51, 61, 71...   |
| `few`    | `n % 10 in 2..4 and n % 100 not in 12..14`                   | 2, 3, 4, 22, 23, 24, 32...     |
| `many`   | `n % 10 == 0 or n % 10 in 5..9 or n % 100 in 11..14`         | 0, 5, 6, 7, 8, 9, 10, 11, 12...|
| `other`  | everything else (fractions)                                  | 1.5, 2.7, ...                  |

English uses two categories: `one` (for `n == 1`) and `other`
(everything else). ICU MessageFormat captures the full set:

```icu
{count, plural,
  one   {# item}
  few   {# items}
  many  {# items}
  other {# items}
}
```

A complete pluralization-category reference for every locale is in
the CLDR Plural Rules table at
<https://cldr.unicode.org/index/cldr-spec/plural-rules>. Translators
should consult that for any new locale.

The api errors namespace currently has zero pluralized strings (the
error envelope is `{ error: "<message>" }` and the messages do not
embed counts). The worker email templates do embed counts (e.g. "you
have N unread notes") and use the `{ count, plural, ... }` ICU form.

## 7. English-only source-artifact rule

CLAUDE.md establishes the constitutional rule: **source artifacts are
English only**. Code, comments, identifiers, log keys, commit
messages, ADRs, and engineering docs are all English. Cyrillic
codepoints are permitted only inside the i18n bundles and a small
allow-list of test fixtures.

The rule is mechanically enforced by `tools/lint-english.ts`. The
allow-list covers:

- `packages/i18n/locales/**`
- `tests/fixtures/i18n/**`
- `**/locales/**` (covers `apps/api/src/i18n/locales/**`,
  `apps/worker/src/i18n/locales/**`, `apps/web/src/locales/**`)
- `**/i18n/__tests__/**` and `**/__tests__/*-i18n.test.*`
- `apps/web/tests/e2e/i18n-russian.spec.ts`
- `speaches-audio.md` (operator-context reference document)

Anything else with Cyrillic codepoints fails the `lint-english` CI
job, breaks the PR, and must be resolved before merge.

### 7.1 audit_log is English-only across all locales

The `audit_log` table is intentionally English-only regardless of the
user's locale. Downstream SIEM tooling, forensic queries, and the
operator UAT scripts assume a single canonical language. The Cyrillic
guard in `apps/api/src/lib/audit.ts` (`assertEnglishOnly`) fails-loud
on any Cyrillic codepoint attempted in an audit-log payload — the
INSERT never happens and the route returns a 500 with the localized
envelope.

If a future audit-log surface needs to capture user-typed content (a
free-text reason field on `account_deletion`, for example), the
recommended pattern is to store the raw user-typed value in a
separate `user_input_audit` table that does NOT enforce English-only,
and keep the audit_log row referring to it by foreign key.

## 8. Email template locale selection

The `users.locale` column (Phase 10 Plan 10-01c migration `0016`) is
the source of truth for an authenticated user's locale preference.
Better Auth's `additionalFields.locale` round-trips it through the
session, so the api can read it without a separate query.

Flow on a verification email:

1. User signs up via `POST /api/auth/sign-up/email`. Better Auth
   captures `Accept-Language` from the request and seeds
   `users.locale` accordingly. The user can change it later via the
   web settings page.
2. Better Auth calls the `sendVerificationEmail` hook configured in
   `apps/api/src/auth.ts`. The hook enqueues an `email-delivery`
   BullMQ job with `payload.locale = user.locale`.
3. The worker pops the job, hands it to `WorkerTemplateRenderer`
   which loads `apps/worker/src/i18n/locales/<locale>/email/<template>/{subject.txt, body.txt, body.html}`.
4. The rendered email goes out via the SMTP transport. The structured
   log emits `event=email.sent, template=email_verification, locale=<locale>`.

If the user's `locale` is null or unset, the renderer falls back to
`en` and emits `event=email.locale_fallback, reason=user_locale_unset`.

## 9. Troubleshooting

### 9.1 Missing key falls back to `en` (not an error)

By design, a missing translation key in `ru` (or any non-source
locale) falls back to `en` rather than throwing. The CI completeness
gate (`i18n-completeness` job) is the place that catches missing
keys, not the runtime. If you see English copy on a Russian page,
the cause is almost always a missing key — check the structured api
log for `event=i18n.missing_key, key=<key>, locale=ru`.

### 9.2 ICU MessageFormat syntax errors

`i18next-icu` will throw at lookup time for invalid ICU syntax. The
api converts this to a 500 with `code: internal_error`. The
structured log carries the failing key and the underlying ICU parser
error. Run `pnpm test:i18n` locally; the unit suite has a parser
sanity check that catches most ICU mistakes pre-merge.

### 9.3 Edge runtime caveats (web)

The Next.js 15 Edge runtime does NOT support `i18next-fs-backend`. The
web bundle uses static-imported JSON instead. Trying to call an
fs-backend from middleware will fail with `Module not found: fs`.
Always use the `apps/web/src/lib/i18n.ts` helpers.

### 9.4 LOCALES_DIR override has no effect after restart

Confirm:

- `LOCALES_DIR` is set in the api + worker env (`docker compose
  config | grep LOCALES_DIR`).
- The mount is readable inside the container (`docker compose exec
  api ls -la $LOCALES_DIR`).
- The override JSON parses (`docker compose exec api node -e
  'console.log(JSON.parse(require("fs").readFileSync(process.env.LOCALES_DIR + "/en/errors.json", "utf8")))'`).
- Check the boot log line `event=i18n.locales_dir, dir=...,
  locales=[...]` — if the dir is empty or missing the line will say
  `event=i18n.locales_dir_fallback, reason=...`.

### 9.5 Verification email arrives in `en` despite `Accept-Language: ru`

The verification email locale comes from `users.locale`, not
`Accept-Language` at the moment of sending. If the user signed up
before the i18n surface landed (or with an older client that did not
send `Accept-Language`), their `users.locale` will be null and the
renderer falls back to `en`. Operator remediation: bulk-update via
`UPDATE users SET locale = 'ru' WHERE locale IS NULL AND created_at <
'2026-05-12'` (or whatever cutover date applies).

### 9.6 Cyrillic appearing in source files

`tools/lint-english.ts` will catch it pre-commit (lefthook) and in
CI (`lint-english` job). If the file is a legitimate i18n surface
(new locale directory, test fixture), add a precise pattern to the
allow-list in `tools/lint-english.ts` and a short justification in
`.planning/phases/10-i18n-docs-oss-housekeeping/deferred-items.md` so
the rationale is recoverable.
